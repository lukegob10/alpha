03 — What keeps the loop reliable

Every path has guardrails

These rules are enforced by the runtime. Prompt text can guide the model, but it does not grant tool access or permission.

▣
One captured view per step

The model step uses a fixed snapshot of model, prompt, transcript, environment, tools, policy, and budget.

⌁
Tools pass policy gates

Visible and executable tools come from the effective tool surface and policy; calls are checked at the effect boundary.

↕
Effects follow safe order

Independent reads may use bounded concurrency. Mutations, approvals, and control-flow work are serialized.

✓
Every call gets a result

Accepted calls end with one structured success, error, denied, or cancelled result tied to the call ID.

▤
History can be replayed

Assistant tool calls and their result receipts are kept together so reload can resume without missing outcomes.

⊣
Child authority stays narrow

Read-only roles stay read-only; workers need explicit write scope, and the parent owns final verification.

04 — Every path has an ending

The engine does not guess at success

A terminal state is explicit. An error, cancellation, or wait for the user cannot silently turn into a successful answer.

✓ Completed

Host completion or visible text passes the completion gate.

◷ Awaiting user

A decision or missing input is needed before safe progress can continue.

⊘ Stopped or needs recovery

Aborted, failed, incomplete, or exhausted work keeps its own outcome.
