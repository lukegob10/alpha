# Fix 12 — trustworthy host and promotion gate evidence

Mode: operational hardening. Scope: the first two false-green defects in
`artifacts/directory-review-2026-10-20/clean-10-validation.md`. This closes the bounded selection and JSON-validation
defects with offline regressions; it does not claim a successful real VS Code host run or broader evaluator closure.

## Fixed now

### High — required host suites could accept a passing subset

The runner inherited `TEST_GREP` even with `--require-all-tests`. Mocha excluded the omitted tests from its counts, so
the production counts validator could not distinguish a full file from a passing subset. Exclusive tests had the same
effect because strict execution did not enable Mocha's `forbidOnly` option. Receipts lacked selection evidence.

- Strict command-line and programmatic runs reject nonempty grep before launching a host. Focused diagnostic runs retain
  grep support. The CLI returns an allowlisted, actionable `unfiltered-suite-required` diagnostic without printing the
  raw pattern.
- The host and runner use the same production Mocha-options helper. Required suites set `forbidOnly: true`, rejecting
  both `test.only` and `suite.only`.
- The host records effective `testSelection: { testFile, grep, forbidOnly }`; runner completion checks bind that observed
  selection to the requested launch before admitting a required run. Final results and harness receipts retain it.
- Full smoke/confidence/extended and independent-outcome admission require a matching file, `grep: null`, and
  `forbidOnly: true`. Existing test-count, exact-host, ownership, provider, retention, and inventory assertions remain.

Receipt compatibility is deliberate: schema version remains 1 and the field is additive. Old schema-1 receipts remain
readable and normalize missing selection to `null`. They cannot prove complete selection and therefore cannot satisfy
a full gate; they must be regenerated by an unfiltered strict run. New filtered/focused receipts likewise cannot satisfy
full admission. Normalization projects only the known selection keys. Test fixtures now describe full selection explicitly
without changing their existing counts or assertions.

### High — malformed promotion JSON could yield `promote: true`

The CLI trusted a TypeScript cast while comparisons silently treated absent/nonnumeric metrics as non-regressions and
truthy strings as boolean evidence. The owning evaluator now accepts `unknown` and parses a strict runtime schema using
the package's existing Zod dependency before applying the existing promotion thresholds.

- Every evidence field is required, booleans are actual booleans, and the primary model is the existing `luna-high` literal.
- Counts are nonnegative safe integers; rates are finite and bounded to `[0, 1]`; cost and duration measurements are finite
  and nonnegative. Relative cost/latency increases must be finite and cannot describe a decrease beyond 100%.
- Holdout passed/safety counts cannot exceed total, pass rates agree with counts, median presence agrees with an empty
  versus nonempty aggregate, and segment counts/rates agree with their enclosing aggregate.
- Unknown top-level/aggregate/segment fields are rejected. Valid aggregate output and negative cost/latency improvements
  retain their existing behavior. Valid evidence with actual threshold/safety failures still returns a nonpromotion
  decision; malformed evidence throws and the existing CLI failure handler exits nonzero.

No production dependency, benchmark threshold, host version, package script, saved task contract, or extension runtime
behavior was changed.
