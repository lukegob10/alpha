## Material findings

### 1. P2: queued-item Steer can target a successor turn

**Trigger:** The user clicks Steer for an already queued message while turn A is displayed. Before queue hydration, serialized steering admission, or claim persistence completes, the same task moves to turn B. Both turns can use the same live `Task` object, so task identity and `canAcceptSteerMessage()` remain valid.

**Evidence:** `webview-ui/src/components/chat/ChatView.tsx:3688` posts `steerQueuedMessage` with task, message and request IDs but no `expectedTurnId`. `src/core/webview/webviewMessageHandler.ts:3827` checks task availability without capturing or checking a turn. `src/core/task/Task.ts:10895` calls `applyQueuedSteeringMessage(messageId)` without its optional guard. That helper checks the guard before and after its awaited queue persistence (`:10911`, `:10921`), but none was supplied. Direct Send-and-Steer already supplies it (`:10884`).

**Upstream contract:** [TurnSteerParams requires expected_turn_id](https://github.com/openai/codex/blob/d571eaf1f61d0d93a797506335a99a9950ffe37b/codex-rs/app-server-protocol/src/protocol/v2/turn.rs#L344); [core rejects a mismatched active turn](https://github.com/openai/codex/blob/d571eaf1f61d0d93a797506335a99a9950ffe37b/codex-rs/core/src/session/turn_input.rs#L837).

**Minimal fix:** Carry the visible turn ID on queued-item Steer; capture a compatibility token at handler admission for historical clients; pass the same invariant guard through serialized steering and claim persistence. Retain the queued message and report `stale_turn` when the token no longer matches. Preserve the separate completed-task queued-follow-up path.

**Regression:** Mirror the existing direct-steering barrier tests at `src/core/task/__tests__/Task.queued-steering.spec.ts:87` and `:144` for queued-item steering. Advance the turn while hydration/admission/claim persistence is held; assert that no successor request or tool is interrupted and the message stays recoverable. Also assert that the UI submits the visible turn ID.

Status: source-confirmed missing invariant; no dedicated failing queued-turn-race test was added or run in this read-only review.

### 2. P3: event-only compatibility projection turns completed/failed into interrupted

**Trigger:** A supported older host sends a valid lifecycle event without `agentLifecycleSnapshot`, invoking the compatibility reducer. Modern publication normally includes the host-reduced snapshot, so this is a compatibility-path defect.

**Evidence:** `webview-ui/src/context/agentLifecycleState.ts:245` groups generic `turn_terminal` with named terminal events, then chooses status from the event name alone at `:252`. Generic terminal events therefore always become `interrupted`, ignoring `payload.status`. The authoritative reducer at `src/core/agent/lifecycle/reducer.ts:568` correctly uses the payload. The shared schema explicitly permits all terminal statuses (`packages/types/src/agent-lifecycle.ts:487`). The fallback path is selected by `applyLifecycleEventToExtensionState()` at `agentLifecycleState.ts:573` when an attached snapshot is absent.

**Runtime reproduction:** Imported the actual webview module with a read-only `pnpm exec tsx` stdin script and passed valid sequence-1 generic terminal events. Output:

```json
{"expected":"completed","actual":"interrupted"}
{"expected":"failed","actual":"interrupted"}
{"expected":"interrupted","actual":"interrupted"}
```

**Upstream contract:** [TurnStatus preserves these distinct outcomes](https://github.com/openai/codex/blob/d571eaf1f61d0d93a797506335a99a9950ffe37b/codex-rs/app-server-protocol/src/protocol/v2/turn.rs#L33).

**Minimal fix:** Handle `turn_terminal` separately using `event.payload.status`. Add a table-driven event-only projection test covering completed/failed/interrupted and a modern attached-snapshot case. A future shared pure reducer could prevent drift, but this defect does not require a broad refactor.

## Intentional differences and limits

- Code and Plan remain user-controlled extension modes. The extension's policy, TODO approval/edit controls, and availability of plan tracking in Plan differ from the terminal product. Upstream currently rejects `update_plan` in Plan mode (`codex-rs/core/src/tools/handlers/plan.rs:87`); Alpha explicitly allows it in the host-restricted Plan tool set (`src/core/agent/ExecutionProfile.ts:69`). Treat this as a deliberate extension capability choice, not a demand to copy terminal mode UX.
- Alpha uses a separate `request_user_input_async` tool/card for nonblocking questions. Current upstream uses a blocking flag on its question protocol and varies availability. The relevant capability is available; exact tool-name parity is unnecessary.
- Manual compaction rejects steering in Alpha, but upstream explicit Compact tasks are also non-steerable (`codex-rs/core/src/session/turn_input.rs:853`). This was checked and is not counted as a gap. Automatic compaction has different control paths and was not treated as equivalent to manual compaction.
- No claim is made about actual UI rendering, screen-reader behavior, keyboard focus, extension activation, or exact-host gate success in the current working tree. Those require the parent-coordinated gates/manual host checks.
