## Meaningful gaps

### G1 — P2: final text is not authoritative after a partial text delta

**Trigger:** a Responses content part yields `response.output_text.delta` with `Hello`, then its completed `output_item.done` and final response contain `Hello world`. Alpha's `textDeltaParts` is a set of seen `(output_index, content_index)` pairs; once any delta arrives, the final complete content is skipped. An injected no-network run produced canonical `text: "Hello"` and successful completion. The same logic applies to refusal text. This is a demonstrated boundary behavior, although the frequency of such abbreviated-delta streams from the live first-party provider was not measured.

**Evidence:** [Alpha final-content projection](F:/roo-fork/Alpha-Code/src/api/providers/openai.ts:1151) (`src/api/providers/openai.ts:1151-1158`); the completion loop also skips already-handled message content at `:1006`. Codex consumes and persists the completed full item in [stream_events_utils.rs at the pinned SHA](https://github.com/openai/codex/blob/d571eaf1f61d0d93a797506335a99a9950ffe37b/codex-rs/core/src/stream_events_utils.rs#L371), with history recording at lines 401–407.

**Smallest fix/test:** track accumulated text by content-part identity, append a missing final suffix once, and fail or deliberately reconcile incompatible final text instead of silently treating it as matching. Add focused streaming cases for partial delta plus full `done`, full content first supplied at `completed`, identical completion without duplication, incompatible content, and refusal parts. Retain current source identity and phase metadata.

### G2 — P2: Responses cache-write usage is discarded

**Trigger:** `usage.input_tokens_details` contains `cached_tokens: 40` and `cache_write_tokens: 60`. Alpha's `processOpenAiResponsesUsage` emits the cached and reasoning counters but no cache-write counter. This affects every caller of that normalizer, including nonstreaming, completed, failed and incomplete responses. Alpha's downstream usage contracts already support cache writes, so the omission propagates as zero/unknown into accounting rather than requiring a new subsystem.

**Evidence:** `src/api/providers/openai.ts:1218-1226`; usage accumulation in `src/core/task/Task.ts:16329-16345`. Codex maps `cache_write_tokens` in [responses.rs:129](https://github.com/openai/codex/blob/d571eaf1f61d0d93a797506335a99a9950ffe37b/codex-rs/codex-api/src/sse/responses.rs#L129) and has an explicit [cache-write regression at line 868](https://github.com/openai/codex/blob/d571eaf1f61d0d93a797506335a99a9950ffe37b/codex-rs/codex-api/src/sse/responses.rs#L868). The no-network experiment reproduced the omission with input=100, cached=40, cache-write=60, output=10 and reasoning=5.

**Smallest fix/test:** normalize `input_tokens_details.cache_write_tokens` into the existing `cacheWriteTokens` field using `providerTokenCount`. Extend the provider outcome fixtures with this field for streamed/nonstreamed completed and error terminals; assert exactly-once additive accounting, including a legitimate zero. No SDK upgrade or persisted-schema migration is needed for the existing field.

### G3 — P3: Responses summaries disappear from the visible reasoning path when opaque reasoning is present

**Trigger:** the normal Responses route requests `reasoning.encrypted_content`; the provider returns an opaque reasoning item with a nonempty readable summary. Alpha buffers `response.reasoning_summary_text.delta`, emits an empty-text reasoning item containing the opaque bytes and summary, and only emits readable summary text when no encrypted item exists. Task's visible reasoning switch ignores empty text, so the readable provider summary is retained for replay but absent from the reasoning UI. Without opaque state, the text is delayed until terminal completion.

**Classification:** an existing tested divergence, not loss of encrypted state. `src/api/providers/__tests__/openai.spec.ts:293` explicitly expects no plaintext reasoning summary in this fixture, so changing it should be a deliberate product/compatibility decision. I did not find a current documented rationale establishing that this suppression is a desired Codex divergence.

**Evidence:** `src/api/providers/openai.ts:840`, `:1031-1034`, `:1127-1137`; `src/core/task/Task.ts:16311-16325`. Codex delivers live readable summaries using either [delta events at turn.rs:3241](https://github.com/openai/codex/blob/d571eaf1f61d0d93a797506335a99a9950ffe37b/codex-rs/core/src/session/turn.rs#L3241) or [completed summary-part delivery at turn.rs:3283](https://github.com/openai/codex/blob/d571eaf1f61d0d93a797506335a99a9950ffe37b/codex-rs/core/src/session/turn.rs#L3283), while retaining opaque reasoning independently.

**Smallest fix/test:** project readable summary text as visible reasoning updates independently from the opaque replay block, with indexed deduplication so history does not acquire duplicate reasoning items. Assert summary visibility before provider completion, exact once-only visible text, unchanged opaque bytes/order, multiple reasoning items/summary parts, and cancellation. Alternatively, document and accept summary suppression as an intentional product divergence, retaining the partial convergence score.

## Intentional or unscored differences

- Additional OpenAI-compatible, Anthropic/Vertex, Gemini and VS Code providers are an intentional extension capability. Normalization into one kernel is aligned with the behavioral goal; additional provider support is not a convergence penalty.
- VS Code host thinking parts and stateful continuation markers have no identical Codex CLI transport. They are the appropriate adapter counterpart, and tested model/vendor/version scoping, source ordering, metadata snapshots and late cancellation are substantial strengths.
- The VS Code 1.125 fallback projects privileged instruction fragments through the host's available User constructor (`src/api/providers/vscode-lm.ts:667`). This is an explicit host compatibility choice, outside this provider-normalization finding set; broader instruction-authority implications belong to the instruction/policy review.
- Codex caches/prewarms WebSockets and can reuse incremental response state (`codex-rs/core/src/client.rs:11-26`); Alpha's inspected OpenAI route sends HTTP Responses requests with complete projected history. Transport reuse and `previous_response_id` are not required to preserve canonical behavior. No matched workload latency/token benchmark was run, so I make no performance-equivalence claim and do not deduct a behavioral point solely for transport selection.
- Current Codex also has optional output-token replay (`codex-rs/core/src/client.rs:1075-1077`) carrying encrypted output beyond reasoning. Alpha preserves reasoning and host-specific state, but this review did not establish that the optional replay feature is required for Alpha's supported public-provider path. It remains unverified/unscored instead of an asserted production defect.
