Proposed designDecision and acceptance criteria

A document belongs to a task, not to a browser session

Give saved HTML a stable identity and an isolated viewer while keeping the source an ordinary editable file.

Status: proposed design. This example explains a decision; it is not the implementation contract for a released feature.

Recommended approach

Store the document’s identity separately from its rendered content. Open an isolated preview from the task record, load only the packaged design kit, and refresh from validated source changes. The document itself receives no extension API.

Decision needed: adopt explicit source refresh for the first release. Automatic refresh can follow once unsaved-editor and external-change behavior have a tested contract.

What a reader should be able to do

  1. Reopen a saved task and find the same report, including after a window reload.
  2. Read conclusions, inspect tables and charts, and follow a source reference through the host’s normal authorization boundary.
  3. Edit the HTML with the existing editor, save it, and deliberately refresh its preview.

A generated page cannot run its own scripts, fetch remote dependencies, invoke commands, or treat a clicked path as permission to read an arbitrary file.

Identity and authority

Document identifier
Opaque and stable within a task. A title is display text, never a storage key.
Source location
Resolved and checked by the host. A renamed or missing file produces a recoverable explanation.
Preview revision
Represents the last successfully loaded source. A failed refresh keeps that revision visible with a clear stale-state notice.

Rendering boundary

HTML contributes semantic content and documented widget data. The host supplies theme values, local kit assets, content policy, and permitted navigation.

The trusted runtime sorts rows and draws charts locally. It has no persistence responsibility and cannot turn a read-only checklist into an approval workflow.

Alternatives and costs

Choice is based on saved-task continuity and a small execution boundary.
Approach Benefit Cost or limitation Decision
Isolated HTML + packaged kit Ordinary source edits; no per-document build Widgets must stay within a documented vocabulary Recommended
Markdown preview only Existing reading and source-link flow Less control over composed findings and interactive data Keep available for ordinary text
Arbitrary page scripts Unrestricted interactions Much larger execution and resource boundary Out of scope

Refresh behavior

  1. The reader saves the source and selects Refresh.
  2. The host resolves the document record and validates the current source against the supported contract.
  3. A valid document replaces the preview as one revision; local sort/filter state resets.
  4. If parsing, lookup, or validation fails, the previous revision stays visible and the reader gets an explanation with a source-edit recovery path.

Unresolved: unsaved editor contents

Use the saved file for the initial release. The viewer must say so when an editor contains unsaved changes. Reading the editor buffer would need a separate definition of revision identity and recovery after a reload.

Acceptance and rollout

  • Required: a saved task reopens the same document after a reload.
  • Required: malformed widget data leaves its semantic table readable.
  • Required: content cannot override host controls or execute document scripts.
  • Required: missing source and unsupported versions explain how to recover.
  • Required: keyboard navigation, contrast themes, narrow views, and text zoom pass in the supported VS Code host.
Rollout and rollback

Ship the first contract version with the viewer and authoring reference together. Exercise the packaged examples before enabling generation guidance. If the viewer cannot load a contract version, preserve the source and offer ordinary editing rather than silently attempting a newer renderer.
