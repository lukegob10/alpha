# Alpha settings review: Codex alignment, approvals, agents, and model controls

Date: **October 10, 2026 (America/New_York)**. This is a review of the current working tree, including pre-existing uncommitted changes. It is not a review of a clean release or a claim that this request introduced the defects below.

## Outcome and scope

The highest-priority defect is an inaccurate consent description: **Auto says sub-agent launches ask for approval, but eligible launches proceed without a dialog**. Five medium-priority findings concern unsaved profile edits, output-token semantics, inapplicable temperature controls, hidden managed-agent settings, and an ineffective MCP checkbox under Full Access. Two low-priority findings concern verbosity plumbing and a dormant approval component.

Alpha already has useful separation between provider configuration, executable modes, approval authority, and bounded child-agent execution. Preserve that architecture. The main alignment opportunity is to explain **where a value comes from, which tasks it affects, when it takes effect, and whether the selected provider supports it**.

Owned review surface: current Codex CLI source and official app/IDE documentation; Alpha approval settings, managed-agent configuration, request/cost limits, advanced terminology, provider/model/profile applicability, and relevant scope boundaries. Other settings are included as navigation context where inspected, not as a claim of exhaustive runtime validation.

**Exactly one sub-agent was launched**, `/root/provider_controls`, for the read-only provider/profile audit. Its evidence and test results are integrated here. No production code, tests, settings, lockfiles, commits, or other reports were changed by this review. This Markdown report is the only authored repository artifact.

### F1 — Auto promises a sub-agent approval dialog that eligible launches skip

**High · must-fix · active-but-confusing · confidence: high.**

Trigger: choose Auto and make an otherwise permitted request that launches an eligible managed agent. The displayed explanation says launches ask for approval, but the host prepares the launch with `requiresExplicitApproval: false`. This is a consent-description defect; it does not establish that a child can escape the parent's policy or that proactive delegation is enabled by default.

Evidence chain:

- [English settings.json:261](F:/roo-fork/Alpha-Code/webview-ui/src/i18n/locales/en/settings.json:261) supplies the inaccurate Auto description; [AutoApproveSettings.tsx:169](F:/roo-fork/Alpha-Code/webview-ui/src/components/settings/AutoApproveSettings.tsx:169) renders it.
- [SettingsView.tsx:395](F:/roo-fork/Alpha-Code/webview-ui/src/components/settings/SettingsView.tsx:395) sends the buffered mode and flags through the typed `updateSettings` contract in [vscode-extension-host.ts:1071](F:/roo-fork/Alpha-Code/packages/types/src/vscode-extension-host.ts:1071).
- [webviewMessageHandler.ts:1046](F:/roo-fork/Alpha-Code/src/core/webview/webviewMessageHandler.ts:1046) persists settings through [ContextProxy.ts:473](F:/roo-fork/Alpha-Code/src/core/config/ContextProxy.ts:473).
- [approval-mode.ts:149](F:/roo-fork/Alpha-Code/packages/types/src/approval-mode.ts:149) derives `alwaysAllowSubagents: true` for Auto. [AlphaProvider.ts:6837](F:/roo-fork/Alpha-Code/src/core/webview/AlphaProvider.ts:6837) intersects parent/live authority; [AlphaProvider.ts:6878](F:/roo-fork/Alpha-Code/src/core/webview/AlphaProvider.ts:6878) resolves launch eligibility and explicit approval. [auto-approval/index.ts:217](F:/roo-fork/Alpha-Code/src/core/auto-approval/index.ts:217) honors that result.

Impact: a user cannot accurately predict the next approval boundary from the mode description.

Smallest follow-up: correct Auto's description to match eligible, bounded launches. If the intended product contract instead requires a dialog for every launch, change the canonical derivation and host approval path together. Preserve child authority narrowing and the separate explicit-only/proactive delegation policy.

Existing coverage/reproducer: [AlphaProvider.subagents.spec.ts:290](F:/roo-fork/Alpha-Code/src/core/webview/__tests__/AlphaProvider.subagents.spec.ts:290) explicitly tests Auto/Bypass launch without a dialog. The focused test selection ran successfully, including narrower Ask/Bypass cases. **This is an executed deterministic runtime contract check, not a newly authored UI-to-host reproducer.** AutoApproveSettings tests mock translation keys and do not assert the real English consent text.

### F2 — Renaming a profile applies unsaved provider edits

**Medium · should-fix · active-but-buggy · confidence: high.**

Trigger: edit a profile's endpoint, key, model, or another provider value without clicking Save, then rename it. [SettingsView.tsx:718](F:/roo-fork/Alpha-Code/webview-ui/src/components/settings/SettingsView.tsx:718) sends the edited `apiConfiguration` directly. Adjacent select/delete/create actions use the unsaved-changes flow. The wire permits the configuration in [vscode-extension-host.ts:982](F:/roo-fork/Alpha-Code/packages/types/src/vscode-extension-host.ts:982); [webviewMessageHandler.ts:2074](F:/roo-fork/Alpha-Code/src/core/webview/webviewMessageHandler.ts:2074) saves it under the new name, preserves the ID, deletes the old name, and activates the replacement at line 2081. Persistence is owned by [ProviderSettingsManager.ts:345](F:/roo-fork/Alpha-Code/src/core/config/ProviderSettingsManager.ts:345), and activation updates the current task's handler in [AlphaProvider.ts:2434](F:/roo-fork/Alpha-Code/src/core/webview/AlphaProvider.ts:2434).

Impact: a name-only operation commits buffered provider changes and can alter a running task's provider configuration while other settings remain unsaved. This violates SettingsView's Save-buffer contract.

Smallest follow-up: rename the persisted profile by stable ID without supplying its edit buffer, or route rename through the established Save/discard workflow. Keep ordinary form inputs bound to `cachedState`.

Existing coverage/reproducer: profile-manager and settings-buffer tests passed. The unsaved-changes suite's manager mock at [SettingsView.unsaved-changes.spec.tsx:211](F:/roo-fork/Alpha-Code/webview-ui/src/components/settings/__tests__/SettingsView.unsaved-changes.spec.tsx:211) exposes create/delete, not this dirty rename path. **No deterministic dirty-rename reproducer was run.** Add that regression in the implementation follow-up.

A bounded reorganization can use existing components and the current typed save path. It does not require a new settings store, policy engine, or provider runtime.

Useful changes to labels are **Model/API profile**, **This task**, **Default for new tasks**, **Managed children per root task**, **Cumulative child input/output tokens**, **Root-tree token/reported-cost budget**, and **Requests/reported API cost between confirmations**. Preserve the current two executable modes and three approval labels; first fix their explanations before proposing broad renaming.

Settings search should find both familiar terms and Alpha's actual labels, reveal the existing group, and retain keyboard focus. Current Codex's search/dependency tests provide a useful UX reference. This is an advisory direction; Alpha search accessibility and performance were not measured in this audit.
