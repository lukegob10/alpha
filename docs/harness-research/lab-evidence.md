# Lab evidence: Anthropic/Claude Code and Google/Gemini harnesses

Research date: 2026-09-18. This note records primary-source evidence about harness design, context, tools, control flow,
evaluation, diagnosis, and revision. It is research input for Alpha Code, not a production change. Public source code is
pinned where possible; moving `main` branches are not immutable evidence. Descriptions are paraphrases, not quotations.

## Synthesis

### State and context

Across A1–A5 and G1–G4, the most stable pattern is to treat a run as a sequence of observable state transitions. The
transcript is diagnostic; the authoritative result is the changed workspace, tested application, persisted record, or
other end state. Handoff files, git state, progress records, compaction, resume history, and runtime prompt composition
are control-flow inputs and need regression coverage.

**Inference for Alpha:** completion and recovery checks should grade canonical lifecycle/tool records plus authoritative
workspace/UI state. Reload, cancellation, compaction, and partial tool-transaction cases deserve explicit multi-step evals.

### Tools and prompts

A4, A5, and G4 converge on tools and prompts as measurable interfaces. Good tools expose distinct workflows, return only
useful context, give actionable errors, and avoid forcing the model to carry low-value data. Gemini’s public source makes
tool visibility and policy state inputs to prompt construction, while Anthropic’s tool work uses held-out tasks and raw
traces to detect wrong tools, redundant calls, and bad parameters.

**Inference:** a tool change should have a realistic workspace case, a neighboring/held-out case, and diagnostics for
selection, arguments, redundancy, errors, and end state. A required tool path should be asserted only when it is itself the
contract.

### Reliability and change control

A1 and G1–G3 show a staged reliability model: fail-first cases, repeated trials, exploratory versus release-blocking
tests, retained logs, provider-noise handling, and baseline comparison. A3 adds one-component-at-a-time removal; G1’s
baseline check distinguishes a PR regression from a failure already present on `main`.

**Inference:** preserve the original failing trace, reproduce before changing the harness, apply the smallest load-bearing
prompt/tool/context/scheduler change, rerun the same case plus a neighbor, and retain or revert from repeated evidence.
Provider failures, grader defects, and agent mistakes should remain separate diagnoses.

### Delegation

A6 and G5 agree that parallel workers help when subtasks are independent and compressible, while coordination can damage
sequential or shared-state work. A3’s planner/generator/evaluator roles work because each has a distinct artifact and
verification boundary. The evidence supports conditional delegation with parent-owned integration and verification, not a
default multi-agent multiplier.

## Limits and Alpha-specific gaps

- Anthropic’s posts are concrete internal case studies but do not release full task banks, raw traces, randomization, or
  confidence intervals. The multi-agent result and long-running comparisons are hypotheses about harness design, not a
  general effect estimate for VS Code coding.
- G1–G4 are directly auditable at a pinned Gemini commit, but thresholds are policy and model/API behavior moves. G2’s
  automatic approval mode leaves approval UX and several policy paths outside the behavioral score.
- G5 was opened/read at arXiv v3; its 260-configuration claim matches the abstract. The orchestrator also read the
  methods/results: its coding evaluations use 20-instance subsets of SWE-bench Verified and Terminal-Bench, limiting
  coding-wide generalization. Its controlled setup is
  stronger for causal claims, but it does not cover Alpha’s extension-host activation, cancellation, persistence/replay,
  or webview projection.
- G6’s fake MCP and isolated homes are valuable deterministic wiring checks; they cannot establish real service latency,
  permissions, or data-distribution behavior. Its simulated user introduces a second model to audit.

## Derived hypotheses for root synthesis

1. Use deterministic lifecycle/tool-contract cases alongside repeated realistic workspace tasks; do not rely on one score.
2. Keep full canonical traces and authoritative end states so failures can be classified rather than guessed from text.
3. Require fail-first reproduction, held-out neighbors, and baseline comparison before retaining prompt/tool/context edits.
4. Gate delegation on decomposability and bounded child scope, with serialized shared-state effects and parent verification.
