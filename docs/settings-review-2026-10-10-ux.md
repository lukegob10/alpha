# Alpha Code settings review: UX, buffering, and active-control inventory

Review date: **2026-10-10, America/New_York**. This is the UX reviewer’s contribution to the broader settings review, not an implementation change.

The principal defects are at the settings boundary: saving an old full snapshot can overwrite newer preferences, renaming a profile commits staged provider edits, and the section tabs lack the keyboard behavior their ARIA roles require. Most controls inspected below remain active and useful. The telemetry opt-in is a dormant-feature candidate with residual onboarding behavior, rather than a completely unused persisted field.

## Scope, evidence, and ownership

- Reviewed all **16 SettingsView entry points**, their buffered versus immediate operations, common navigation/search primitives, and Save/Cancel/Discard/resync/profile flows.
- Deep runtime traces cover UI/general settings, notifications, context management, checkpoints, terminal integration, experiments, custom tools, language, and About/telemetry. Provider/model details and mode/prompt semantics belong to the other review reports. MCP and Worktrees runtime findings belong to the original reviewer; this report includes their integration with the settings buffer.
- **Exactly two sub-agents were launched in this chat:** `settings_inventory` and `settings_buffering`. Both completed read-only work. The parent independently inspected the two highest-impact persistence paths, traced the owned runtime controls, and ran additional deterministic probes. No further sub-agents were launched.
- Alpha HEAD at the initial inspection was `b0423c06af2341c89948ec2a68f56ffd3e6f037a`. The checkout already contained extensive unrelated and concurrent changes. Findings describe the reviewed working tree, not an assertion that every cited line belongs to that commit. A concurrent English-settings locale change was inspected and did not change the cited Enter/custom-tools/telemetry wording.
- Root `AGENTS.md`, the clean-code-review skill, and the openai-docs skill were applied. The assigned review-only boundary takes precedence over the clean-code-review skill’s usual implementation workflow.
- **This review writes only this document.** No production code, tests, configuration, lockfiles, generated artifacts, or commits were changed by this reviewer or its sub-agents.
- Severity describes impact; priority describes the follow-up recommendation. “Active-but-buggy” means the control has a real consumer but violates a contract. “Active-but-confusing” means the wiring works but the presentation misstates it. “Dormant/stale candidate” requires more evidence before removing the persisted contract. No completely dead user-visible control was confirmed in the deep-owned surfaces.

The host compatibility target remains **VS Code 1.125.0**. Live host behavior was not tested in this read-only review.

### UX-01 — Save overwrites unrelated newer host preferences

**Trigger and impact.** Open Settings, edit only volume, receive a same-profile refresh that disables sound and changes approval mode from Auto to Ask, and click Save. The form sends its original sound and approval values along with the volume edit. This is an unintended preference rollback, including a security-sensitive preference; it is **not evidence that an existing task’s policy enforcement can be bypassed**.

**Owning boundary.** [SettingsView.tsx:157](F:/roo-fork/Alpha-Code/webview-ui/src/components/settings/SettingsView.tsx:157) snapshots the entire extension state. Hydration/profile/import effects reseed the buffer, but ordinary refreshes do not rebase untouched fields. [SettingsView.tsx:399](F:/roo-fork/Alpha-Code/webview-ui/src/components/settings/SettingsView.tsx:399) saves the complete cached payload, including approval mode at 407 and sound at 432. [vscode-extension-host.ts:1071](F:/roo-fork/Alpha-Code/packages/types/src/vscode-extension-host.ts:1071) carries `updatedSettings?: AlphaCodeSettings` without a baseline revision. [webviewMessageHandler.ts:953](F:/roo-fork/Alpha-Code/src/core/webview/webviewMessageHandler.ts:953) writes every supplied field through [ContextProxy.ts:473](F:/roo-fork/Alpha-Code/src/core/config/ContextProxy.ts:473). A real competing writer is the public configuration API at [api.ts:509](F:/roo-fork/Alpha-Code/src/extension/api.ts:509).

**Reproduction actually run.** Unmodified SettingsView mounted with real React, Testing Library, and JSDOM; child controls, extension context, and bridge were mocked. After editing volume to `0.8` and refreshing sound to `false` and approval to `ask`, Save posted sound `true`, approval `auto`, and volume `0.8`. A source-extracted host-handler probe also persisted the untouched stale sound value. The parent independently checked the current full-payload and unconditional-write code. Confidence: **high**.

**Smallest follow-up.** Keep edits in `cachedState`, track dirty fields, rebase untouched fields, and save a changed-field patch. Detect conflicts when an externally changed field is itself edited. Apply equivalent conflict protection to provider-profile saves. Existing refresh tests protect an intentionally edited provider field; they do not cover collisions on unrelated fields.

### UX-02 — Rename saves and activates staged provider edits

**Trigger and impact.** Edit a model, endpoint, or credential without main Save, then rename the profile. Rename passes the staged provider configuration directly to the host and activates it. A metadata operation therefore implicitly commits unrelated form edits and can rebuild the current task’s provider.

**Trace.** [SettingsView.tsx:718](F:/roo-fork/Alpha-Code/webview-ui/src/components/settings/SettingsView.tsx:718) posts `renameApiConfiguration` with cached `apiConfiguration`, without `checkUnsaveChanges`, and advances the name ref. [ApiConfigManager.tsx:141](F:/roo-fork/Alpha-Code/webview-ui/src/components/settings/ApiConfigManager.tsx:141) validates the new name but knows nothing about staged fields. The host reads only the old ID at [webviewMessageHandler.ts:2071](F:/roo-fork/Alpha-Code/src/core/webview/webviewMessageHandler.ts:2071), saves the client configuration under the new name at 2074, deletes the old profile, then activates the new one. [ProviderSettingsManager.ts:345](F:/roo-fork/Alpha-Code/src/core/config/ProviderSettingsManager.ts:345) validates/stores profiles and [ProviderSettingsManager.ts:624](F:/roo-fork/Alpha-Code/src/core/config/ProviderSettingsManager.ts:624) writes SecretStorage. Activation copies the configuration and rebuilds the provider at [AlphaProvider.ts:2414](F:/roo-fork/Alpha-Code/src/core/webview/AlphaProvider.ts:2414).

**Reproduction actually run.** Mounted SettingsView posted the unsaved model on Rename without a discard dialog while main Save remained enabled. The source-extracted host case changed `saved-model` to `unsaved-model`, deleted the original profile, and activated the unsaved model while retaining the ID. The parent independently checked this host path. Confidence: **high**.

**Smallest follow-up.** Rename persisted metadata using persisted profile contents, while retaining staged provider edits until Save. ApiConfigManager’s existing tests cover name validation and callbacks, not this persistence boundary. Credential writes were traced, not exercised against real SecretStorage.

### UX-03 — Settings tabs lack keyboard navigation

**Trigger and impact.** Focus the selected Providers tab and press the navigation keys expected for a tab list. Other sections cannot be selected through the tabs: unselected triggers have `tabIndex=-1`, and the component implements no arrow-key handler.

**Trace.** [Tab.tsx:58](F:/roo-fork/Alpha-Code/webview-ui/src/components/common/Tab.tsx:58) clones children without keyboard navigation. [Tab.tsx:81](F:/roo-fork/Alpha-Code/webview-ui/src/components/common/Tab.tsx:81) sets `role="tab"`, `aria-selected`, and roving-looking tab indices, but handles only clicks. [SettingsView.tsx:965](F:/roo-fork/Alpha-Code/webview-ui/src/components/settings/SettingsView.tsx:965) uses this primitive for all 16 sections. The list also lacks vertical orientation and tab/panel associations; TabContent does not provide a tabpanel role. In compact layout, the `.tab-label` text is hidden and no explicit trigger label was found at [SettingsView.tsx:978](F:/roo-fork/Alpha-Code/webview-ui/src/components/settings/SettingsView.tsx:978); the compact accessible-name concern is source-derived, not separately reproduced with the live CSS.

**Reproduction actually run.** Actual TabList/TabTrigger components in JSDOM: ArrowDown and ArrowRight changed neither selection nor focus, and the next Tab skipped UI/Notifications for a trailing button. SettingsView tests substitute the tab components and navigate through `targetSection` rerenders at [SettingsView.spec.tsx:332](F:/roo-fork/Alpha-Code/webview-ui/src/components/settings/__tests__/SettingsView.spec.tsx:332). Confidence: **high** for keyboard failure; live assistive-technology behavior remains unverified.

**Smallest follow-up.** Implement keyboard selection/focus in the shared primitive, with vertical arrows and Home/End, explicit compact names, and correct tab/panel relationships. Test the real primitive in wide and compact settings layouts. The expected semantics are documented by the [W3C tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) (retrieved 2026-10-10).

### UX-04 — Save clears dirty state before persistence succeeds

**Trigger and impact.** Click Save while storage is delayed or rejects. Save immediately disables itself and Done can exit before any host result. Separate global/profile/telemetry/debug writes can partially apply. The terminal inherit-environment baseline also advances before its VS Code write succeeds, so the next unrelated Save need not retry that failed change.

**Trace.** [SettingsView.tsx:478](F:/roo-fork/Alpha-Code/webview-ui/src/components/settings/SettingsView.tsx:478) posts separate messages; 489 updates the terminal baseline and 492 clears dirty state. [vscode.ts:44](F:/roo-fork/Alpha-Code/webview-ui/src/utils/vscode.ts:44) is a fire-and-forget bridge. The host awaits sequential writes at [webviewMessageHandler.ts:1046](F:/roo-fork/Alpha-Code/src/core/webview/webviewMessageHandler.ts:1046) without a correlated settings result or rollback. [ContextProxy.ts:324](F:/roo-fork/Alpha-Code/src/core/config/ContextProxy.ts:324) updates its memory cache before the ordinary global-state write completes. Global message failures are logged at [AlphaProvider.ts:1879](F:/roo-fork/Alpha-Code/src/core/webview/AlphaProvider.ts:1879); profile failures notify and return `undefined` at [AlphaProvider.ts:2308](F:/roo-fork/Alpha-Code/src/core/webview/AlphaProvider.ts:2308). Neither restores the form’s dirty state. The allowlisted VS Code write at [webviewMessageHandler.ts:1707](F:/roo-fork/Alpha-Code/src/core/webview/webviewMessageHandler.ts:1707) also has no Save acknowledgement.

**Reproduction actually run.** The mounted component disabled Save and allowed Done without a dialog before any host processing. A rejected injected `contextProxy.setValue` in the source-extracted handler propagated while the already-returned UI remained clean. Real storage failure and a complete multi-message partial-write transaction were not run. Confidence: **high** for the missing acknowledgement boundary.

**Smallest follow-up.** Correlate Save with authoritative success/failure, retain dirty or pending state and the terminal baseline until success, and explicitly report partial application. Existing suites assert dispatched payloads, not pending navigation or failure recovery.

Other Worktrees/MCP defects are owned by the original reviewer and are not additional findings in this ledger.

### UX-07 — Staged custom-tools enablement executes discovery before Save

**Trigger and impact.** Toggle custom tools on in the local edit buffer. [CustomToolsSettings.tsx:39](F:/roo-fork/Alpha-Code/webview-ui/src/components/settings/CustomToolsSettings.tsx:39) immediately requests `refreshCustomTools` when its cached `enabled` prop becomes true. The host at [webviewMessageHandler.ts:2023](F:/roo-fork/Alpha-Code/src/core/webview/webviewMessageHandler.ts:2023) loads configured directories. **Smallest follow-up.** Keep executable loading behind committed enablement, or make an explicit immediate action and its effects clear. If a pre-Save preview is required, use non-executing metadata inspection. Add a host-side contract for the intended boundary. The `refreshCustomTools` wire variant is already shared at [vscode-extension-host.ts:911](F:/roo-fork/Alpha-Code/packages/types/src/vscode-extension-host.ts:911).

Confidence: **high** for the source path. No actual tool module was executed to demonstrate side effects. This review did not exhaustively audit workspace trust or outer host guards, and does **not** claim a confirmed security bypass. The finding concerns the Save/Discard contract and executable preview behavior.

### UX-08 — Custom-tools refresh retains deleted tools and hides failures

**Trigger and impact.** Delete a previously loaded custom-tool file and click Refresh. Loading scans current files but does not reconcile the registry’s existing map, so the deleted tool remains in the returned catalog. A later broken file is collected in `LoadResult.failed` but the handler ignores that result, making an incomplete refresh look successful.

**Trace.** [custom-tool-registry.ts:57](F:/roo-fork/Alpha-Code/packages/core/src/custom-tools/custom-tool-registry.ts:57) loads into an existing map; per-file failures are collected at 85 and directory results are aggregated at 124. `clear()` exists at 222 but is not used by this refresh path. [webviewMessageHandler.ts:2026](F:/roo-fork/Alpha-Code/src/core/webview/webviewMessageHandler.ts:2026) awaits loading without consuming its `failed` collection, then sends `getAllSerialized()`. The tool builder at [build-tools.ts:399](F:/roo-fork/Alpha-Code/src/core/task/build-tools.ts:399) also uses the shared registry. Catalog reconciliation should therefore protect current-step descriptors as well as future visibility.

**Reproduction actually run.** Unmodified TypeScript registry source was transpiled in memory and exercised with fake filesystem/module imports. Initial `first.js` loaded `first`; after the directory became empty, the new load returned no loaded tools but the registry still advertised `first`. A broken import returned one failed item while retaining `first`. A source-extracted host-case probe supplied a failed load result and observed only `{type: "customToolsResult", tools: []}` without an error. No real files or custom modules were used. Confidence: **high** for deletion and failure reporting; cross-workspace effects were source-derived, not separately reproduced.

**Smallest follow-up.** Reconcile a fresh scoped directory snapshot atomically, retain immutable descriptors for accepted in-flight calls, and expose per-file/partial failures in the typed result and UI. Test deletion, replacement, directory-scope changes, and mixed valid/invalid modules. Existing registry tests cover loading/merging and absent directories; no equivalent UI-refresh regression was identified. This finding does not assert that stale tools escape the canonical approval gate.

## Healthy contracts worth preserving

- Ordinary provider and global form edits remain isolated in `cachedState` until Save. Controls should continue to use that buffer; direct live-state binding would create another lost-edit path.
- Cancel in the unsaved-changes dialog retains the draft. Discard restores the latest host state. Done and application-tab navigation use the guard. Profile load/create/delete also use it; creation after accepted discard uses the latest provider configuration.
- Automatic model initialization and semantic provider no-op synchronization avoid marking initialization as an edit. Managed-agent defaults/save normalization retain compatibility fields.
- Terminal inherit-environment is buffered and the host permits only its allowlisted VS Code setting. This narrow host write boundary should remain.
- Known experiments, compaction scope/post-turn thresholds, diagnostics limits, image limits, notification controls, checkpoint recovery, and all three UI settings have live consumers. No evidence supports wholesale settings removal.
- Scroll restoration, ResizeObserver/event-listener cleanup, existing VS Code theme-token patterns, English resources, and reduced-motion styling were present in the reviewed paths. These source checks do not substitute for visual/high-contrast or live keyboard verification.
- Built-in skills, native Tickets, previews, scheduled tasks, execution approvals, and Alpha’s security/workspace boundary remain first-class capabilities under the repository contract. This review proposes no removal or replacement runtime.
