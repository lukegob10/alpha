# Token Usage Optimization Without Losing Agent Power

This document explains why Alpha's token usage grows quickly, where the expensive prompt content enters the request flow, and how to reduce token cost while preserving the extension's strongest behavior: reading code, editing safely, running tools, using context, and continuing long tasks.

This is a design document only. It does not propose removing capability. The goal is to keep the agent powerful while making each call more selective, more cacheable, and easier to measure.

## Executive Summary

Alpha uses a lot of tokens because every model request can include:

- A generated system prompt.
- Native tool definitions.
- Conversation history since the last summary or truncation.
- Tool calls and tool results.
- Retrieved file contents.
- Codebase search snippets.
- Dynamic `environment_details`.
- Rules from global settings, project files, mode files, `AGENTS.md`, `.alpha`, and legacy `.roo`/`.cline` files.
- Current mode metadata.
- Open tabs, visible files, terminal output, git status, cost, current time, and todo reminders.

The extension works well because it gives the model a lot of operating context. The cost problem is that much of this context is resent on every call, even when it is stale, redundant, already known, or only weakly relevant.

The highest-impact improvements are:

1. Add token attribution by prompt section and message type.
2. Move volatile context later and keep stable prompt prefixes stable.
3. Reduce repeated `environment_details`.
4. Compact tool outputs before they enter history.
5. Use retrieval budgets based on tokens, not only result counts.
6. Summarize earlier and more incrementally.
7. Preserve file awareness through compact file manifests and folded definitions instead of full repeated file content.
8. Simplify visible modes so prompts and tool sets are more stable.
9. Cache system prompt sections by content hash.
10. Make "Ask" genuinely lightweight and "Code" powerful.

## Request Anatomy

The runtime path is primarily in `src/core/task/Task.ts`.

Each API call is built from:

- `systemPrompt`: generated by `SYSTEM_PROMPT` in `src/core/prompts/system.ts`.
- `cleanConversationHistory`: produced from effective API history, with images optionally removed and consecutive user messages merged.
- `metadata`: includes native tool definitions and provider-specific request data.

The final request is sent through:

`this.api.createMessage(systemPrompt, cleanConversationHistory, metadata)`

That means token cost is not just the user's latest message. It is the current system prompt plus selected history plus tool schemas plus any dynamic state and tool outputs preserved in history.

## Major Token Sources

### 1. System Prompt

The system prompt includes:

- Mode role definition.
- Markdown formatting section.
- Tool-use section.
- Tool-use guidelines.
- Capabilities.
- Full modes list.
- Skills section.
- Rules section.
- System info.
- Objective.
- User custom instructions, global instructions, mode instructions, rule files, ignore rules, `AGENTS.md`, and generic project rules.

This content is valuable, but not all of it needs to change every request. The system prompt should be treated as a set of separately measurable sections, not as one opaque string.

### 2. Tool Definitions

Tool definitions are not pasted into the prose prompt, which is good. They are passed as native tool schemas.

They still count against provider context or request payload size in most APIs. Large schemas, many tools, and MCP tools can materially increase every call.

Tool filtering already happens in `src/core/task/build-tools.ts` and `src/core/prompts/tools/filter-tools-for-mode.ts`. The opportunity is to make filtering more aggressive and measurable without taking away the right tool when needed.

### 3. Conversation History

`apiConversationHistory` persists API-facing messages. The effective history is filtered by `getEffectiveApiHistory` after condensation or truncation.

History grows from:

- User messages.
- Assistant text.
- Tool uses.
- Tool results.
- File contents returned by tools.
- Command output.
- Codebase search results.
- Error messages.
- Summaries.

Tool results are often the largest part because file reads, search output, and terminal logs can be verbose.

### 4. Environment Details

`src/core/environment/getEnvironmentDetails.ts` can inject:

- Visible files.
- Open tabs.
- Active and inactive terminal output.
- Recently modified files.
- Current time.
- Current cost.
- Git status.
- Current mode and model.
- Workspace file listing.
- Todo reminders.

This is useful but highly volatile. Volatile content undermines prompt caching and adds tokens repeatedly.

### 5. File Reads And Search Results

Full file reads are expensive and become part of history. If a file is read early and then read again after edits, both versions may remain in history until condensation.

Codebase search is cheaper than reading many files, but retrieved snippets still cost chat-model input tokens after they are returned as tool output.

### 6. Condensation

Context management lives in `src/core/context-management/index.ts` and `src/core/condense/index.ts`.

When token thresholds are reached, Alpha can summarize conversation history and keep a fresh-start summary. This is good, but condensation itself is another model call and the summary can include folded file context plus automatic environment details.

Condensation reduces future requests, but if it happens too late, the user still pays for many large calls before the summary appears.

## Why Tokens Build So Quickly

The token curve is multiplicative:

1. A user asks for work.
2. The system prompt is attached.
3. Environment details are attached.
4. The model calls tools.
5. Tool outputs enter history.
6. The next request sends the prompt plus prior tool outputs.
7. More tools produce more outputs.
8. Context grows until condensation or truncation.

The expensive pattern is "read, paste, keep, repeat."

Examples:

- A file is read in full. The full text enters history.
- A command returns hundreds of lines. The output enters history.
- A codebase search returns many chunks. The chunks enter history.
- Environment details repeat open tabs, current time, terminal state, and file listings.
- The next model call sees all of it again.

The agent feels powerful because it remembers everything. The cost problem is that it remembers too literally.

## What Should Be Preserved

Do not optimize by making the agent blind.

Preserve:

- The user's latest intent.
- The task plan and outstanding todos.
- Files edited and why.
- Files read and relevant symbols.
- Exact patches applied.
- Test commands and outcomes.
- Errors that are still unresolved.
- API/tool call continuity required by providers.
- Safety rules and project instructions.
- Enough recent conversation to maintain trust and continuity.

Reduce:

- Repeated static instructions.
- Verbose environment state that did not change.
- Old command output after it has been interpreted.
- Full file bodies after relevant facts are extracted.
- Duplicate search results.
- Repeated mode lists and descriptions.
- Long generic rules that do not apply to the current task.
- Tool schemas for tools unavailable or unlikely in the current mode.

## Measurement First

Before changing behavior, add a token ledger for each call.

Recommended buckets:

- System prompt total.
- System prompt by section.
- Tool schema total.
- Conversation history total.
- Latest user message.
- Environment details.
- File read outputs.
- Command outputs.
- Codebase search outputs.
- MCP outputs.
- Images.
- Summary messages.
- Folded file context.
- Cached input tokens.
- Cache write tokens.
- Cache read tokens.
- Output tokens.
- Total request cost.

The extension already has usage concepts such as input tokens, output tokens, cache reads/writes, and cost. The missing piece is attribution: knowing which section caused the spike.

Without attribution, token optimization becomes guesswork.

## Optimization Strategy

### 1. Section-Level Prompt Accounting

Generate the system prompt from named sections with stable IDs:

- `mode.roleDefinition`
- `formatting`
- `toolUse`
- `toolGuidelines`
- `capabilities`
- `modesList`
- `skills`
- `rules`
- `systemInfo`
- `objective`
- `customInstructions`

For each section, compute:

- Character count.
- Token count.
- Content hash.
- Stability class: stable, semi-stable, volatile.
- Source files or state keys.

This gives the UI and logs an immediate answer to "why was this call so big?"

### 2. Stable Prefix Discipline

Prompt caching rewards stable prefixes. The beginning of the prompt should change as little as possible.

Keep early:

- Product/system policy.
- Tool-use policy.
- Base role framing.
- Stable safety rules.

Move later:

- Current mode list.
- Skills list.
- Rule files that change often.
- Dynamic model state.
- Environment details.
- Current time, cost, open tabs, terminal output.

Avoid changing the first lines of the prompt when switching between similar implementation modes. If Code becomes the primary capable mode and orchestration becomes internal, the prefix becomes more stable.

### 3. Environment Details Delta Mode

`environment_details` should become delta-based after the first turn.

First turn can include:

- Workspace file overview.
- Visible files.
- Open tabs.
- Current mode.
- Basic environment.

Later turns should include only changes:

- Newly visible file changed from X to Y.
- New terminal output since last retrieval.
- Recently modified files.
- New git changes only if enabled.
- Todo changes.

Current time and current cost should be optional. They are useful for transparency, but they change every call and can reduce prompt cache reuse.

Recommended behavior:

- Include current time only when a task is time-sensitive or setting is enabled.
- Include current cost in UI, not in model context, unless the model is explicitly asked to reason about cost.
- Include git status only on first turn, before commit-related tasks, or when files changed.
- Include terminal output as a capped delta with a summary after it is interpreted.

### 4. Tool Output Compaction

Tool outputs should have two forms:

- Full raw output for the UI and local storage.
- Compact model-facing output for API history.

Examples:

- `read_file`: return full content initially, then preserve a file digest and relevant ranges.
- `execute_command`: return exit status, command, working directory, last relevant lines, and an omitted-output count.
- `search_files`: return grouped matches with caps per file.
- `codebase_search`: return top results with token budget, not just count.
- `list_files`: return tree summary and omitted count for large directories.

The model does not need every repeated byte forever. It needs enough to decide the next action.

### 5. File Memory Instead Of Full File Retention

When a file is read, create a compact file memory record:

- Path.
- Last seen hash.
- Relevant symbols.
- Relevant line ranges.
- Why it was read.
- Whether it was edited.
- Last edit summary.
- Whether it must be re-read before editing.

Then future calls can include file memory instead of full content. If exact content is needed, the agent can re-read the file.

This keeps power because the agent still has access to files. It just stops carrying full file bodies when summaries are enough.

### 6. Retrieval Budgets

Codebase search settings currently include score threshold and max results. Add a token budget.

Recommended defaults:

- Ask mode: smaller retrieval budget.
- Code mode: medium retrieval budget.
- Debug mode: medium-high retrieval budget for stack traces and related files.
- Explicit "deep search": larger budget.

Every retrieval result should count against:

- Max snippets.
- Max snippets per file.
- Max total tokens.
- Max characters per snippet.
- Minimum score threshold.

Also deduplicate:

- Overlapping chunks from the same file.
- Adjacent chunks that can be merged.
- Identical snippets returned by multiple searches.

### 7. Earlier, Incremental Condensation

Current context management condenses when a configured threshold is reached. That avoids context window failures but can still allow many expensive requests before condensation.

Better strategy:

- Use lightweight rolling summaries earlier.
- Summarize completed tool cycles.
- Summarize command outputs after interpretation.
- Summarize file reads into file memory after they are used.
- Keep a short recent window plus durable task memory.

This avoids a huge late condensation event and keeps each request flatter.

### 8. Split UI History From Model History

The user should still see rich details. The model does not always need them.

Store:

- Full transcript for UI.
- Full raw tool outputs for audit/debug.
- Compact API history for future model calls.
- Durable task memory for continuity.

This preserves transparency while reducing repeated prompt payload.

### 9. Tool Schema Minimization

Tool definitions are structured, but they still have size.

Options:

- Keep Ask mode tool schemas minimal: read/search/MCP only.
- Keep Code mode powerful, but do not include image generation, slash commands, or codebase search unless enabled and configured.
- Include MCP tools only when MCP is enabled and relevant.
- For very large MCP sets, expose a discovery tool instead of every MCP tool schema.
- Collapse aliases and avoid duplicate tool definitions.
- Avoid verbose descriptions in native schemas when the system prompt already explains usage.

This preserves power because tools can still be enabled when needed, but unused surfaces stop taxing every call.

### 10. Mode Simplification For Cache And Cost

Visible mode sprawl increases prompt and behavior variability.

Recommended visible modes:

- Ask: low-token explanation and analysis.
- Code: full implementation mode.
- Debug: investigation and repair.

Make orchestration an internal behavior of Code. This reduces the number of role definitions, tool profiles, and mode lists that need to be considered in normal use.

Mode-specific power can still exist behind the scenes through skills, task templates, or hidden sub-behaviors.

## Ask Mode Should Be Lightweight

Ask should not carry Code's full operating burden.

Ask defaults:

- No edit tools.
- No command tools unless explicitly escalated.
- Smaller environment details.
- No full workspace file listing after first turn.
- Lower codebase search result budget.
- Compact responses by default.
- Do not include implementation-specific tool instructions unless available.

This makes Ask cheap and fast while preserving the ability to inspect code.

## Code Mode Should Stay Powerful But Selective

Code should still have read, edit, command, MCP, codebase search, todo, and completion tools where enabled.

Optimization should come from:

- Better context selection.
- Compact tool outputs.
- Rolling task memory.
- Token-aware retrieval.
- Prompt caching.
- Stable section ordering.
- Avoiding repeated full context.

Do not remove core tools from Code just to save tokens. Make Code smarter about when and how much context it carries.

## Debug Mode Should Prioritize Evidence

Debug can spend more tokens than Ask, but it should spend them differently.

Debug should preserve:

- Error messages.
- Stack traces.
- Reproduction steps.
- Test commands.
- Logs that support or disprove hypotheses.
- Files touched during diagnosis.

Debug should compact:

- Repeated logs.
- Long successful command output.
- Full files that were only used to locate one failing function.
- Duplicate stack traces.

Debug-specific summaries should track hypotheses and evidence, not just conversation history.

## Prompt Caching Recommendations

Prompt caching helps only when repeated prefixes remain stable.

Actions:

- Keep stable policy and role text first.
- Move volatile context late.
- Avoid current time/cost early in prompts.
- Avoid changing mode prefix unnecessarily.
- Keep tool schema order deterministic.
- Sort rule files deterministically, which the repo already attempts.
- Hash prompt sections and detect accidental churn.
- Report cached token usage in the UI.

OpenAI prompt caching is automatic for supported models with sufficiently long repeated prefixes. Anthropic supports explicit caching patterns and recommends placing stable content before volatile content. The implementation should be provider-aware, but the product rule is universal: stable first, volatile last.

## Code Index And Embedding Cost

Embeddings help only when they reduce larger chat-model input.

Good use:

- Find relevant files in large repos.
- Avoid reading many files blindly.
- Return compact snippets before exact reads.
- Use semantic search when filenames are unknown.

Bad use:

- Search repeatedly with broad queries.
- Return too many chunks.
- Inject chunks without reading exact files before editing.
- Index generated/vendor/build files.
- Re-index unchanged files.

Optimization:

- Token cap search output.
- Deduplicate chunks.
- Use file path and symbol metadata heavily.
- Prefer smaller snippets with exact line ranges.
- Add "search result used" telemetry.
- Tune thresholds per embedding model.
- Use hybrid lexical/vector search for precision.

## Response Token Control

Output tokens matter too.

The agent should be concise by default in Code and Debug:

- Explain what changed.
- Mention files.
- Mention tests.
- Mention blockers.
- Avoid restating large code.
- Avoid long summaries of tool outputs unless requested.

Ask mode can be more explanatory, but should still avoid repeating full source snippets unless needed.

For code edits, the model should not paste whole files into the response. The file system already contains the changes.

## Proposed Token Budget Defaults

These are conceptual budgets, not hard-coded numbers:

### Ask

- Small environment context.
- Small retrieval budget.
- No command/edit schemas.
- Summarize old context aggressively.
- Favor explanation over tool loops.

### Code

- Medium environment context.
- Medium retrieval budget.
- Full core coding tools.
- Compact command/file outputs after use.
- Preserve task memory and changed file summaries.

### Debug

- Medium environment context.
- Higher budget for recent errors/logs.
- Compact repeated logs.
- Preserve hypotheses and evidence.

### Orchestration Internals

- Very small parent context.
- Child tasks receive scoped context only.
- Parent stores child summaries, not full child histories.

## Proposed Task Memory Model

Add or formalize a durable task memory object:

- `goal`: current user goal.
- `constraints`: explicit user constraints.
- `plan`: active plan/todos.
- `filesRead`: path, hash, purpose, relevant ranges.
- `filesEdited`: path, summary, status.
- `commandsRun`: command, cwd, outcome, relevant output summary.
- `openIssues`: blockers and unresolved questions.
- `decisions`: important choices and rationale.
- `retrievals`: queries and useful results.

Include this compact memory in context instead of replaying old raw material.

These are likely high-value areas for future implementation work:

- `src/core/environment/getEnvironmentDetails.ts`: delta mode and tighter defaults.
- `src/core/task/Task.ts`: compact API history, raw UI history separation, and request token ledger.
- `src/core/context-management/index.ts`: earlier incremental condensation strategy.
- `src/core/condense/index.ts`: summary size controls and folded context budget.

## Anti-Patterns To Avoid

Avoid:

- Removing tools globally to save tokens.
- Making the agent ask the user before doing obvious inspection.
- Summarizing away exact edit state before tests run.
- Hiding important tool outputs from both UI and model.
- Relying only on embeddings instead of exact file reads before edits.
- Making summaries so abstract that the agent loses concrete file paths and decisions.
- Condensing only at the edge of the context window.
- Treating cached tokens as free; they still may have cost and latency implications depending on provider.

## Recommended Roadmap

### Phase 1: Observability

- Add token attribution by section and message category.
- Show per-call token breakdown in developer diagnostics.
- Log prompt section hashes.
- Track cache read/write tokens.
- Track top token contributors per request.

### Phase 2: Low-Risk Reductions

- Move time and cost out of model context by default.
- Cap terminal output deltas.
- Cap git status output.
- Token-budget codebase search results.
- Compact list/search outputs.
- Lower folded file context default or make it adaptive.

### Phase 3: Model-Facing History Compaction

- Separate full UI transcript from compact API history.
- Summarize tool cycles after completion.
- Replace old full file reads with file memory.
- Preserve exact current files through hashes and re-read prompts.

### Phase 4: Prompt Cache Optimization

- Stabilize prompt section order.
- Keep stable sections first.
- Reduce mode churn.
- Hash and memoize prompt sections.
- Provider-specific cache controls where supported.

### Phase 5: UX Simplification

- Make Ask cheap.
- Make Code the main powerful agent.
- Make Debug evidence-driven.
- Move Orchestrator behind Code as an internal capability.
- Keep advanced custom modes available but not central to the default experience.

## Success Metrics

Track:

- Median input tokens per call.
- P90 input tokens per call.
- Tokens by source category.
- Cost per completed task.
- Number of model calls per completed task.
- Condense frequency.
- Average tokens before first condensation.
- Cache hit ratio.
- Cache read/write tokens.
- Tool output tokens per task.
- File read tokens per task.
- Codebase search tokens per task.
- User-visible task success rate.
- Edit/test success rate.
- Re-open/re-read rate caused by over-compaction.

The target is not minimum tokens. The target is fewer wasted tokens with equal or better completion quality.

## Bottom Line

Alpha's token usage grows quickly because it keeps rich context in the model loop: full prompts, dynamic environment details, tool outputs, file contents, search results, and conversation history.

The fix is not to weaken the agent. The fix is to make context intentional:

- Stable prompt content should be cached and kept stable.
- Volatile environment content should be delta-based.
- Raw tool outputs should be compacted for the model.
- File awareness should become structured memory.
- Retrieval should have token budgets.
- Condensation should happen incrementally, not only near the limit.
- Ask should be lightweight, while Code remains powerful.

With those changes, Alpha can keep the behavior that makes it useful while dramatically reducing per-call token growth.
