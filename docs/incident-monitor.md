# Alpha incident monitor

The incident dashboard is an extension-host presentation of canonical task lifecycle events. It is enabled by the existing `alpha.debug` setting. **Alpha: Incident Dashboard** appears in Alpha's top three-dot overflow menu in the sidebar and editor panel in an installed extension or the Extension Development Host. It does not create a second task runtime. The **Start debugging task** action creates one ordinary primary `Task` through `AlphaProvider.createTask`, which continues through `AgentTurnEngine`.

## Event semantics

- The monitor observes lifecycle events only after the journal accepts and the projector applies them. Each entry uses the canonical task, run, turn, sequence, and event identity. Presentation labels are fixed text; opaque IDs are hashed for display and investigation references.
- A terminal failed turn or task is an incident. A tool error is displayed in the timeline as evidence, but may be recovered by the agent and therefore does not alone assert task failure. Cancellation, interruption, approval waits, and a long-running healthy step are states, not failures. Projection gaps or conflicting events are marked as incomplete evidence; the monitor does not infer that the task failed.
- Diagnostic tasks carry a persisted `diagnosticSession` marker. The monitor excludes their events and history so investigations cannot trigger a loop. Disabling debug mode stops new observation and hides the dashboard entry point. The incident notification is emitted by the extension host when the event arrives, independent of model availability.
- On opening after webview reload or extension-host restart, the host seeds at most 12 recent tasks from task history and a bounded tail of each lifecycle journal. Historical incidents remain visible but are not renotified. A missing journal is marked absent; malformed or changed evidence is marked incomplete. Neither status is converted into a failure claim.

## Turn exploration

The dashboard also lists the recent turns seen in that bounded task and journal window. A completed turn remains completed even when the agent recovered from a tool error; terminal failure remains a separate status. The positive filter selects completed turns without a recorded tool error. The error filter includes terminal failures and turns with a recorded tool error, including recovered errors. Running, cancelled, and interrupted turns remain distinct. Summary cards are computed from the displayed sample, so they are not lifetime totals or reliability rates for the whole installation.

The initial snapshot carries at most 64 compact turn rows. Selecting a row requests its detail from the extension host; the detail has at most 40 fixed-kind event records and is sent only for the selected turn. The UI keeps the table visible while detail loads and ignores stale responses after a different row is selected. A user can start a diagnostic task from either a completed or failed turn. The task is read-only under the existing diagnostic policy and does not modify the source task.

Turn row IDs are opaque hashes of task, run, and turn identity. Tool names are accepted only from the known tool registry. The webview receives counts, terminal status, timestamps, and fixed event kinds, never prompt text, model output, tool arguments, tool results, or arbitrary error strings. Missing or truncated journal evidence is identified as incomplete rather than filled in from an assumption.

## Evidence and authority

The dashboard carries status, timestamps, fixed event labels, hashed references, and evidence completeness. It does not send prompts, tool arguments, tool output, provider payloads, file contents, or arbitrary error strings to the webview. On a user click, the host calls the existing `collectDiagnosticsEvidence` redaction pipeline and builds a bounded prompt. The prompt separates observed facts from explicitly unverified hypotheses and gives the model next checks. It does not include a source-checkout path or assume the current workspace contains Alpha's source.

Diagnostic sessions have a persisted allowlist at the `TaskToolSurface` boundary. The same captured policy filters both model-visible schemas and execution. They cannot use shell, file mutation, MCP, task creation, managed delegation, or task lifecycle controls, even if a provider replays a hidden tool call. The session may read only through its vetted built-in readers. The user click is the only creation trigger; the failing task is not modified.

## Bounds and verification

- In memory and on the wire: 12 tasks, 8 timeline entries per task, 12 alerts, 64 recent turn rows, and 40 event records for the selected turn. A panel update is coalesced over 100 ms. History loading reads at most 128 KiB per journal, 256 parsed events per task, and three files concurrently. Incident prompt output is capped at 12 KiB.
- The monitor performs no model call or file read on a live lifecycle event. A notification is requested only for a newly observed alert. Diagnostics evidence files are read only after a click, using the existing 4 MiB per-source limit and redacted projections. Read-only task directory resolution creates no storage directories and rejects paths that escape the configured task root.
- Validate with focused monitor, diagnostic policy, webview, and provider tests; extension type checks; and the VS Code 1.122.1 smoke gate. Measure event projection with a fixed synthetic event stream before claiming an overhead result. The intended live-event budget is under 1 ms per event on the extension host and no synchronous I/O.

The repeatable local workload is `pnpm --dir src exec tsx core/agent/benchmarks/AgentIncidentMonitor.benchmark.ts`. On Node 24.14.1 / Windows, seven paired runs of 512 canonical phase events measured a projector-only median of 487.38 ms and a projector-plus-monitor median of 493.97 ms with one dashboard listener. The paired median increment was 9.33 ms (1.9%). Individual increments ranged from -27.82 to 51.97 ms while the VS Code host gate was running, so these figures are a noisy capacity check, not a general overhead claim. A separate 10,000-event monitor capacity pass took 106.42 ms with one listener; 1,000 snapshots took 0.46 ms. The same fixed script can be rerun on an idle host for release comparisons.

For the turn table change, the previous implementation was measured on Node 24.14.1 / Windows with the same synthetic stream: 512-event paired median monitor overhead was 13.63 ms (seven pairs), 1,000 one-task snapshots took 0.47 ms, and 10,000 capacity observations took 92.85 ms. After the change, one run of the same script recorded a paired median overhead of 8.79 ms, 1,000 one-task snapshots in 0.55 ms, and 10,000 capacity observations in 106.97 ms. The new bounded 64-turn workload took 22.28 ms for 1,000 snapshots and 2.96 ms for 1,000 selected-turn detail reads. Paired overhead varied substantially across runs, and the before/after commands ran from different local checkouts, so these are capacity observations rather than a claim of a general speedup. No synchronous I/O was added to the event path.

The first-paint regression uses one delayed task-history gate and one delayed journal read, each 25 ms. With that identical scripted workload, the old awaited snapshot returns after 50 ms of controlled delay; the dashboard now returns its in-memory snapshot before either delay and publishes hydrated data when the read completes. Both paths perform one journal read. This tests the loading order and read count rather than wall-clock performance on a production workspace.

## Upstream comparison

Checked the current Codex CLI source at `openai/codex` commit `f53f5a6fed662bd6f352d08066925c871a061182` on 2026-09-28. Its [protocol](https://github.com/openai/codex/blob/f53f5a6fed662bd6f352d08066925c871a061182/codex-rs/docs/protocol_v1.md) distinguishes turn completion, errors, approvals, and interruption. Its [turn implementation](https://github.com/openai/codex/blob/f53f5a6fed662bd6f352d08066925c871a061182/codex-rs/core/src/session/turn.rs) drains tool futures and preserves cancellation as a separate terminal path; its [tool router](https://github.com/openai/codex/blob/f53f5a6fed662bd6f352d08066925c871a061182/codex-rs/core/src/tools/spec_plan.rs) filters exposed specs through policy. The [approval tests](https://github.com/openai/codex/blob/f53f5a6fed662bd6f352d08066925c871a061182/codex-rs/core/tests/suite/approvals.rs) cover approval as a distinct flow. Alpha follows these observable principles in its own journal and tool surface rather than copying Codex's runtime structure.

Rechecked the [Codex CLI execution event schema](https://github.com/openai/codex/blob/main/codex-rs/exec/src/exec_events.rs) on 2026-09-29. It distinguishes `turn.started`, `turn.completed`, and `turn.failed` from item events. Alpha's dashboard uses its own lifecycle journal and preserves the same distinction between turn outcomes and intermediate item errors.
