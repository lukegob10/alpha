# Evaluation harness research and implementation plan

Alpha has substantial deterministic regression coverage and a useful real-extension evaluation architecture. The audit's
most urgent findings were grading rules that could accept incomplete work, inconsistent evidence guarantees between
evaluation paths, and a coding task bank supporting narrower claims than some labels suggested. The implementation pass
repairs many of those boundaries; its verification and remaining limits are recorded separately below. Complete the
remaining admission work before using aggregate scores to justify quality improvements.

This plan combines the 20-agent repository audit with primary-source research retrieved on **2026-10-23**. The repository
baseline is **5112f0d816e6897af5922a6799218f8b7e43a6b1**. It covers the evaluator, fixtures, live Copilot campaigns,
extension-host and webview tests, certification, CI, performance measurement, and Codex alignment. The finding register
contains 60 consolidated items, including explicitly marked research-driven proposals. A subsequent 20-agent
implementation pass added the changes recorded in the completion ledger below; remaining gaps are explicit.

## Decisions and boundaries

Keep the real Alpha extension as the system under test. Extend `packages/evals`, `apps/vscode-e2e`, and
`scripts/harness`; reuse their graders, campaign runner, receipts, identities, and statistics. Preserve the shared
execution kernel, canonical tool policy, existing protections, and historical records. Changes to persisted contracts
need additive fields, backward-compatible readers, and tested migration or explicit legacy-unavailable behavior.

Keep VS Code **1.138.0** as the exact reference host and **1.125.0** as the installation minimum. Use Node **24.21.0**,
pnpm **11.24.0**, and existing package commands. Evaluate model behavior through the actual extension and its provider
adapters. Borrow benchmark preparation and verifier techniques without introducing another agent runtime or copying
Codex prompts or implementation.

Treat these as distinct claims: deterministic contract correctness, observed live product behavior, coding task quality,
performance, model comparison, and Codex behavioral alignment. A report must identify which claim its evidence supports.
An algorithm-repair task about compaction does not establish that Alpha survives compaction. One passing live trial is a
canary result, not an estimate of general reliability. These distinctions follow OpenAI's evaluation methodology and
product-harness research [S02, S03], and the claim-dependent reliability analysis [S14].

Retain independent outcome checks. Trace checks should enforce actual lifecycle, authority, and explicitly required
process contracts; they should not require one preferred solution strategy when another valid implementation fulfills
the request. Preserve unknown measurements rather than inventing zero values. Grader or infrastructure failures must
remain distinguishable from an agent failing a valid task.

## What the research changes

1. **Validate the evaluator before scaling the benchmark.** OpenAI's July 2026 audit documents overly strict tests,
   missing requirements, misleading prompts, and insufficient coverage. It withdraws the earlier recommendation to adopt
   SWE-bench Pro. Replacing Alpha's task bank with a different benchmark brand would not resolve oracle validity [S04,
   S05]. Require meaningful correct alternatives and incomplete-solution controls alongside reference solutions.
2. **Test the deployed combination of model and harness.** OpenAI's September plugin study found stable aggregate
   results alongside substantial per-case verdict changes. Compare shared cases across component and actual-product
   boundaries; record per-case consistency and actual configuration [S02]. The recent Harness-Bench work supports
   inspecting artifacts, execution feedback, and delivery completeness, with the limitations recorded below [S13].
3. **Target the model-to-harness boundary with meaningful mutations.** The October HarnessTester preprint emphasizes
   contract-faithful setups for code driven by model output. Use selected mutations to prove that Alpha's assertions
   catch wrong outcomes, lost signals, malformed tool intent, and incorrect lifecycle transitions [S12]. Coverage counts
   alone cannot establish this.
4. **Add combinations of lifecycle transitions and shipped defaults.** Anthropic's April postmortem shows why isolated
   tests and internal configurations can miss regressions involving reasoning history, idle sessions, effort defaults,
   and prompt interactions [S10]. Apply this lesson to Alpha through its existing adapters and immutable step contracts.
5. **Control resources and sampling explicitly.** Infrastructure configuration can change outcomes, and repeats do not
   create new independent tasks [S09, S14, S15, S16]. Preserve the existing clustered comparisons; make their decision rule,
   coverage, denominators, and evidence sufficiency explicit.
6. **Verify effects under attack.** Source-to-effect testing, adversarial grading controls, and separate measures of
   clean utility, attacked utility, attempted violations, and realized effects improve interpretation [S24-S29]. A model
   refusal does not exercise enforcement; a denied effect does not establish model resistance.

The research establishes design lessons, not measurements of Alpha. Practitioner reports and recent preprints carry
different evidentiary weight. No external benchmark's reported defect rate, speedup, reliability, or resource multiplier
is an Alpha estimate.

## Priority and evidence definitions

- **P0 / High / must-fix:** address before relying on the affected scoring, attribution, or campaign result.
- **P1 / High / should-fix:** materially improves run reliability, release evidence, or protection of important boundaries.
- **P2 / Medium / should-fix:** expands capability coverage or strengthens interpretation and maintenance.
- **P3 / Low / advisory:** later research or operational expansion after the prerequisites are trustworthy.

Evidence codes: **R** means a bounded audit probe reproduced the behavior; **C** means current source or wiring establishes
the finding; **G** means a scoped coverage gap, not a demonstrated product failure; **D** means a research-driven proposal
requiring an initial gap check. IDs identify findings; implementation order is defined by the work packages below.

## Implementation sequence

## Initial realistic workload

Use twelve real-repository tasks as an **authoring pilot**, spanning at least six repositories and TypeScript/React,
Python, and a compiled ecosystem. These counts are a tractable proposed starting point, not a statistically sufficient
reliability sample. Allocate eight development tasks and four sealed confirmation tasks across separate repositories or
independent task families. Preserve the existing twelve-task Frontier roster until a deliberately versioned replacement
is approved; the four-task pilot does not silently satisfy that older contract.

| Pilot family                     | Required behavior                                                                                            | Independent acceptance                                                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Shared-contract feature          | Coordinate shared schema, provider/core consumer, UI projection, and tests.                                  | New behavior works, old records still load, consumers agree, and regression tests execute.                             |
| Repository debugging             | Find the cause across callers with plausible distractors and minimal implementation hints.                   | Original bug fails before the fix; specified edge cases and preserved behavior pass afterward.                         |
| Concurrent correctness           | Repair idempotency/cancellation/backpressure with overlapping work.                                          | Barrier-controlled simultaneous requests, cancellation before/during work, failure cleanup, and no duplicate effects.  |

| Build/configuration repair       | Diagnose actual toolchain or configuration precedence failure.                                               | Reproducible install/build/test, correct supported configuration, and no suppression of required verification.         |

Each task needs a visible requirement-to-check map, untouched baseline, valid reference, materially different valid
alternative when practical, and incomplete/wrong/tampering controls. Where a unique specified representation precludes
a different implementation, record the reason and vary nonessential implementation choices. Use maintainer review to
judge ambiguous requirements and audit samples of both successes and failures. A model judge may help triage; it does
not approve its own generated task without independent evidence.

Keep hidden tests/reference answers and future Git objects outside agent-readable task environments. History-based
exercises may expose explicitly permitted history ending at the task's base revision; future solution commits, gold
patches, hidden acceptance files, and answer-revealing metadata remain inaccessible. Normal development tests remain
available. For independently isolated verification,
transfer declared final artifacts into a fresh trusted environment using Alpha's existing execution and grading
boundaries. Harbor's separate-verifier pattern is an implementation reference, not a requirement to migrate runners
[S19]. Pre-certify dependency/build environments on intended operating systems [S20, S21].

Track task, environment, and verifier versions separately. Changed prompts, tools, resource constraints, or task sets
normally require new agent runs. Verifier-only changes may permit regrading complete retained artifacts if no newly
required runtime observation is missing. Preserve original verdicts and link amended ones. A compromised, saturated,
unsolvable, or publicly solved task needs explicit quarantine/retirement and a versioned replacement [S18, S29, S30].

## Measurement and decision contract

Extend existing schemas rather than creating another report store. Each comparison should preserve:

- Claim and surface: contract, product quality, model comparison, performance, or behavioral alignment.
- Task roster/version, strata, family/repository identity, weights, grader identity, and allowed differences.
- Actual Alpha build, source, host, provider/model/extension identity, effective effort/options, policy, and profile owner.
- Resource allocation and hard ceilings, enforcement, concurrency, cache protocol, network/dependency conditions, and time
  blocks. Counterbalance or randomize baseline/candidate order within blocks.
- Planned, started, terminal, valid, scoreable, failed, blocked, cancelled, timed-out, and missing cells; original samples
  remain separate from preparation, retries, reproductions, and repairs.
- Outcome, safety/effect evidence, final-report truthfulness, retained artifacts, requests, tokens, known costs, latency
  phases, and cleanup. Partial diagnostic metrics can survive a failed attempt without making it successful.
- Predeclared primary outcome, material margin, spending cap, review schedule, and keep/revise/revert/inconclusive rule.

Publish end-to-end delivery across the scheduled workload and, when justified, conditional capability across valid
trials. Explain every exclusion by arm. Product timeouts, incorrect denials, task-budget exhaustion, and model-caused
tool failures must not disappear into an infrastructure exclusion. Keep failed grader execution and independently
established provider/environment outages distinct. For paired conditional analysis, preserve comparable pairs and
report dropped pairs explicitly; report sensitivity to the exclusion policy.

Label first-attempt success, retry-assisted success, empirical consistency, pass-at-k, and all-attempt success separately.
Do not use diagnostic retries to inflate independent sample counts. Retain related tasks and both arms together when
resampling at the repository/family level. A fixed-bank conclusion need not pretend to generalize to future tasks.
Model-neutral claims require appropriate provider/model coverage; ordinary Alpha release comparisons can keep the
deployed system fixed without introducing competing runtimes [S08, S14-S17].

Use a small repeated pilot to estimate instability and paired discordance, then choose a confirmatory budget based on
the intended effect margin, coverage, clustering, and decision error tolerance. Three repeats can expose case flipping;
they do not certify 98% reliability or a reliable ranking. Do not repeatedly inspect ordinary confidence intervals until
they become favorable; either use a fixed declared decision schedule or a justified sequential method.

For a quality-preserving optimization, define delta as candidate quality minus baseline quality. Establish
noninferiority only when the predeclared one-sided lower confidence bound exceeds the negative material margin, and
the separate cost/latency objective is met. Absence of a significant difference is insufficient. If the approved budget
cannot resolve the margin, report inconclusive. Critical authority, data-integrity, and safety invariants remain hard
failures. Zero observed violations is not proof of zero future risk.
