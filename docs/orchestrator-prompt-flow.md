# Orchestrator, Modes, Prompt Flow, and Code Indexing

This document explains how Alpha currently builds prompts, how modes such as Ask, Code, Debug, and Orchestrator work, how the code index and embeddings fit into the loop, and where the design is carrying avoidable complexity.

The main conclusion: Alpha has two different concepts named like "orchestrator."

- `orchestrator` mode is a user-facing agent mode. It delegates work to child tasks through `new_task`.
- `CodeIndexOrchestrator` is an internal service that scans files, creates embeddings, writes vectors, and keeps the code index fresh.

Those two systems are unrelated at runtime except that both can indirectly affect the agent experience. Treating them as one thing makes the architecture feel much more confusing than it is.

## Source Map

The relevant files are:

- `packages/types/src/mode.ts`: built-in mode definitions, including `architect`, `code`, `ask`, `debug`, and `orchestrator`.
- `src/shared/modes.ts`: mode lookup, mode merging, tool-group expansion, and prompt override resolution.
- `src/core/prompts/system.ts`: the main system prompt assembly function.
- `src/core/webview/generateSystemPrompt.ts`: webview preview path for generating the same system prompt.
- `src/core/task/Task.ts`: task lifecycle, API conversation storage, context management, tool building, and model request execution.
- `src/core/task/build-tools.ts`: native tool array construction and mode-based tool filtering.
- `src/core/prompts/tools/filter-tools-for-mode.ts`: tool permission filtering by mode, model, MCP availability, experiments, disabled tools, and code-index readiness.
- `src/core/tools/NewTaskTool.ts`: implementation of child-task delegation.
- `src/core/tools/CodebaseSearchTool.ts`: implementation of semantic codebase search.
- `src/core/environment/getEnvironmentDetails.ts`: dynamic context appended to user turns.
- `src/core/prompts/sections/custom-instructions.ts`: user/project rules, mode rules, `AGENTS.md`, `.alpharules`, `.alpha/rules`, and language preference injection.
- `src/services/code-index/*`: code-index configuration, scanning, parsing, embeddings, vector storage, search, and indexing orchestration.
- `.alphamodes`: project-local custom modes.
- `AGENTS.md`: repository guidance injected into prompts when agent rules are enabled.

## What A Mode Is

A mode is configuration, not a separate agent implementation. The schema lives in `packages/types/src/mode.ts`.

Each mode has:

- `slug`: stable identifier such as `code`, `ask`, `debug`, or `orchestrator`.
- `name`: display label.
- `roleDefinition`: the first and most influential text in the system prompt.
- `whenToUse`: description shown in the generated `MODES` section.
- `description`: UI summary.
- `customInstructions`: extra mode-specific instructions appended later in the prompt.
- `groups`: tool permission groups, sometimes with file restrictions.

Built-in modes currently include:

- `architect`: read, markdown edit, MCP. Intended for planning.
- `code`: read, edit, command, MCP. Intended for implementation.
- `ask`: read, MCP. Intended for explanation and analysis without changes.
- `debug`: read, edit, command, MCP. Intended for diagnosis and fixes.
- `orchestrator`: no normal tool groups. It is intended to coordinate work by creating child tasks.

Custom modes can come from extension global state and project configuration. Project modes in `.alphamodes` add more specialized roles such as issue-fixer, PR fixer, merge resolver, docs extractor, issue investigator, and issue writer.

## How Mode Resolution Works

Mode resolution happens in `src/shared/modes.ts`.

The important behavior:

1. Built-in modes come from `DEFAULT_MODES`.
2. Custom modes are loaded from stored `customModes`.
3. If a custom mode has the same slug as a built-in mode, it replaces the built-in mode.
4. If a custom mode has a new slug, it is appended.
5. Prompt overrides come from `customModePrompts`.
6. For built-in modes, prompt overrides can replace the role definition and custom instructions.
7. For custom modes, the custom mode definition is treated as the source of truth.

This means there are three layers that can change what a mode does:

- The built-in mode definition.
- A custom mode with the same slug.
- A prompt override for that mode.

That layering is powerful, but it also makes "what prompt am I actually using?" hard to answer without a preview or trace.

## The System Prompt: Where It Is And What It Contains

The main system prompt is generated by `SYSTEM_PROMPT` in `src/core/prompts/system.ts`.

The prompt is not a single static file. It is assembled every request from stable sections plus dynamic state.

Current assembly order:

1. Current mode role definition.
2. Markdown formatting rules.
3. Shared tool-use policy.
4. Tool-use guidelines.
5. Capabilities section.
6. Modes section listing every available mode and when to use it.
7. Skills section, filtered for the current mode.
8. Rules section.
9. System information section.
10. Objective section.
11. User custom instructions, global instructions, mode instructions, mode-specific rules, ignore rules, `AGENTS.md`, and generic rules.

The system prompt starts with the mode role definition. For example:

- Code starts as a skilled software engineer.
- Ask starts as a technical assistant focused on answers and information.
- Debug starts as a debugger.
- Orchestrator starts as a strategic workflow coordinator.

After that, the same shared scaffold is appended. That means modes differ mostly by role definition, custom instructions, and tools, not by having separate agent engines.

## Prompt Preview Flow

`src/core/webview/generateSystemPrompt.ts` is used by the UI to preview the prompt.

It:

1. Reads provider state.
2. Gets the selected mode from the webview message or falls back to the default mode.
3. Loads custom modes.
4. Creates a temporary API handler to inspect model metadata.
5. Calls `SYSTEM_PROMPT(...)` with context, cwd, MCP hub, mode, custom prompts, custom modes, global custom instructions, language, ignore rules, settings, and skills manager.

This preview path should be treated as a diagnostic surface. If the product wants users to understand mode behavior, this is the place to expose "what will actually be sent."

## Runtime Request Flow

The task loop is primarily in `src/core/task/Task.ts`.

At a high level:

1. A task is created with a selected mode.
2. The task stores user-visible messages in `clineMessages`.
3. The task stores model/API messages in `apiConversationHistory`.
4. User content is processed for mentions.
5. Environment details are generated and appended around user turns.
6. Context management may condense or truncate history before the request.
7. Native tools are built and filtered for the current mode.
8. `SYSTEM_PROMPT` is generated.
9. The API handler receives:
    - system prompt,
    - cleaned conversation history,
    - metadata including tools and other provider details.
10. The model streams assistant content and tool calls.
11. Tool calls are parsed and executed.
12. Assistant and tool result messages are persisted.
13. The loop repeats until completion, user interruption, error, or delegation.

The important point: the system prompt is sent alongside every model request. It is generated fresh because mode, rules, MCP, tools, skills, language, model settings, and current state can change.

## Dynamic Context Injection

The prompt is not the only injected context. `src/core/environment/getEnvironmentDetails.ts` produces an `environment_details` block that is attached to user turns.

This can include:

- Visible VS Code files.
- Open tabs.
- Running terminals and new terminal output.
- Recently modified files.
- Current time and timezone.
- Current cost.
- Current mode slug, name, and model.
- Workspace file listing on initial or file-detail turns.
- Git status, if enabled.
- Todo reminders, if todo lists are enabled.

This is a useful feature but a major source of prompt volatility. Anything placed in `environment_details` is likely to change from turn to turn, which can reduce prompt-cache hit rates and increase input tokens.

The current system prompt even warns the model that `environment_details` is auto-generated and not directly written by the user.

## User Rules And Project Rules Injection

`src/core/prompts/sections/custom-instructions.ts` appends the `USER'S CUSTOM INSTRUCTIONS` section.

The order is:

1. Language preference.
2. Global custom instructions.
3. Mode-specific custom instructions.
4. Mode-specific rules.
5. Ignore-controller instructions.
6. `AGENTS.md`, `AGENT.md`, and `AGENTS.local.md` content if agent rules are enabled.
7. Generic rule files.

Rule sources include:

- Global `.alpha/rules`.
- Project `.alpha/rules`.
- Optional subfolder `.alpha/rules`.
- Legacy `.roo/rules`.
- Legacy `.alpharules`.
- Legacy `.clinerules`.
- Mode-specific `.alpha/rules-{mode}`.
- Legacy `.alpharules-{mode}` and `.clinerules-{mode}`.
- `AGENTS.md` and `AGENT.md`.

This is a lot of input surfaces. It explains why behavior can feel unpredictable: the final prompt can be affected by project files, home-directory files, extension state, mode overrides, and settings.

## Tool Availability By Mode

Tools are not embedded as a giant catalog in the system prompt. The comment in `src/core/prompts/system.ts` explicitly says the tools catalog is not included in the system prompt.

Instead, tools are passed through provider-native tool calling. `src/core/task/build-tools.ts` builds the tool array, then `src/core/prompts/tools/filter-tools-for-mode.ts` filters it.

Filtering considers:

- Current mode groups.
- Always-available tools.
- Mode file restrictions.
- Model-specific excluded and included tools.
- Tool aliases.
- Whether code indexing is enabled, configured, and initialized.
- Whether todo lists are enabled.
- Whether image generation or slash-command experiments are enabled.
- Disabled tools from settings.
- MCP availability and MCP resources.

This is the right direction: tool definitions belong in API tool metadata, not in prose inside the system prompt. It reduces prompt bloat and gives providers structured function schemas.

## Ask, Code, Debug, And Orchestrator

The current modes exist for understandable reasons:

- Ask is valuable because it prevents accidental edits and keeps the interaction analysis-oriented.
- Debug is valuable because diagnosis has a different operating style from normal implementation.
- Code is valuable as the default implementation mode.
- Orchestrator is valuable only when true child-task delegation is a product goal.

The questionable part is separating "orchestrator" from "code" as a mode users must choose for normal coding work.

If the desired experience is "Codex-style coding agent that can plan, inspect, edit, run commands, and delegate when helpful," then Orchestrator and Code should probably not be peer modes in the user's mental model. The product can expose:

- Ask: answer and analyze, no edits unless explicitly escalated.
- Debug: diagnose and fix failures, with stronger investigation behavior.
- Code: implement changes.

Then orchestration becomes an internal capability of Code, not a top-level mode the user must understand. In that model, "orchestrator set to code" is exactly right: the agent can coordinate work, but its primary posture is still code execution.

## Current Orchestrator Mode

The built-in `orchestrator` mode has `groups: []`.

Its custom instructions say it should:

- Break complex work into subtasks.
- Use `new_task` to delegate to specialized modes.
- Include all needed context in the child task.
- Track child task results.
- Synthesize outcomes when all subtasks are done.
- Ask clarifying questions when needed.

Because `groups` is empty, Orchestrator does not have normal read/edit/command capability from its group list. It depends on always-available tools and `new_task`.

This makes it a coordinator, not a coder. That is conceptually clean, but it creates friction when the user expects "orchestrator" to be the best coding mode.

## Child Task Delegation

`new_task` is defined in `src/core/prompts/tools/native-tools/new_task.ts` and implemented in `src/core/tools/NewTaskTool.ts`.

The model must provide:

- `mode`: child mode slug.
- `message`: child task instructions.
- `todos`: optional markdown checklist, required if the workspace setting requires todos.

The implementation:

1. Validates required params.
2. Checks whether todos are required.
3. Parses the markdown checklist if provided.
4. Validates that the requested target mode exists.
5. Asks the user to approve the delegation.
6. Calls `delegateParentAndOpenChild`.
7. Returns a tool result that the task was delegated.

`Task.ts` has extra protections around `new_task`:

- `new_task` must be called alone.
- Tools after `new_task` in the same assistant message are truncated.
- Error tool results are injected for truncated tool calls.
- Assistant messages are saved before tool execution so tool results do not appear before their matching tool calls.

Those protections exist because delegation changes task ownership and persistence ordering.

## Where State Is Stored

There are several storage layers:

- `context.globalState`: custom modes, custom mode prompt overrides, code-index global config, auto-enable defaults, and other global settings.
- `context.workspaceState`: workspace-specific code-index enablement.
- VS Code secrets: API keys and sensitive code-index provider credentials.
- Task storage under global storage: API conversation history and UI task messages.
- Code index cache: `roo-index-cache-{workspaceHash}.json` in extension global storage.
- Vector store:
    - LanceDB local index path by default.
    - Qdrant collection named from a workspace path hash if Qdrant is selected.
- `.alphamodes`: project-level custom mode definitions.
- Project and global rule files: `.alpha`, `.roo`, `.alpharules`, `.clinerules`, `AGENTS.md`.

The important design smell: behavior-defining data is split across extension state, secrets, project files, home-directory files, and vector stores. That makes the live behavior hard to inspect and hard to reproduce.

## Code Indexing And Embeddings

The code index is a retrieval system. It does not place the entire codebase into the prompt.

The flow is:

1. `CodeIndexManager` initializes the feature for a workspace.
2. `CodeIndexConfigManager` loads configuration and secrets.
3. `CodeIndexServiceFactory` creates:
    - embedder,
    - vector store,
    - parser,
    - directory scanner,
    - file watcher.
4. `CodeIndexOrchestrator` starts indexing.
5. `DirectoryScanner` lists workspace files.
6. `.alphaignore`, ignore rules, supported extensions, excluded directories, and file size limits filter the file set.
7. `CodeParser` splits files into semantic code blocks using tree-sitter where possible and fallback chunking where needed.
8. File content hashes are compared against the cache.
9. Changed blocks are batched.
10. The embedder converts block text into vectors.
11. The vector store writes vectors plus payloads such as file path, line range, code chunk, file hash, and segment hash.
12. The file watcher keeps the index updated.

Search flow:

1. The model calls `codebase_search`.
2. The query is embedded.
3. The vector store returns nearest code chunks above the configured score threshold.
4. Results are formatted as file path, score, line range, and code chunk.
5. Those result snippets enter the conversation as tool output.

## Does Embedding Code Save Tokens?

Embedding code does not make tokens free and does not magically compress the codebase into the model context.

It saves tokens when it prevents large irrelevant file content from being sent to the chat model. Instead of sending many full files, the system sends a smaller set of retrieved chunks.

It can increase cost when:

- The codebase is indexed repeatedly because cache invalidation is too aggressive.
- Search results are too many or too large.
- The model repeatedly calls `codebase_search` when simpler lexical search or file reads would work.
- Retrieved chunks are poor matches, causing follow-up searches and reads.
- Embedding provider cost plus vector-store overhead exceeds the saved chat-model input tokens for small workspaces.

It improves quality when:

- The query is semantic and exact filenames are unknown.
- The workspace is large enough that listing and reading likely files is expensive.
- Chunks preserve useful symbols, line ranges, and paths.
- Search thresholds and result limits are tuned.
- The agent uses retrieval as a first pass, then reads exact files before editing.

Embeddings are a retrieval index. The chat model still pays input tokens for every retrieved chunk that is injected into the prompt as tool output.

## Prompt Caching And Token Cost

Prompt caching is separate from embeddings.

Embeddings reduce what you choose to send. Prompt caching discounts or accelerates repeated prompt prefixes that are sent again.

OpenAI states that prompt caching is automatic for supported models on prompts longer than 1,024 tokens, caching the longest previously computed prefix in increments of 128 tokens, and exposes `cached_tokens` in usage data. OpenAI also notes caches are generally cleared after several minutes of inactivity and within an hour of last use.

Anthropic documents a more explicit cache model where the cache prefix covers `tools`, `system`, and `messages` in order up to a cache breakpoint. Anthropic recommends placing stable content at the beginning and volatile content after it. Anthropic also documents cache read/write pricing differences and minimum cacheable prompt lengths by model.

For Alpha, this matters because the current prompt has a mix of stable and volatile pieces:

Stable:

- Mode role definition.
- Markdown formatting rules.
- Tool-use policy.
- General capabilities.
- Most mode definitions.
- Most static project rules.
- Most tool schemas.

Volatile:

- Current time.
- Current cost.
- Open tabs and visible files.
- Terminal output.
- Recently modified files.
- Git status.
- Todo reminders.
- Full workspace file listing.
- Dynamic MCP resources.
- Changing custom mode state.
- Search results and tool outputs.

To improve cache hit rates, stable content should stay in the earliest prefix, and changing content should move as late as possible.

## Does The Current Prompt Shape Help Caching?

Partially.

Good:

- The system prompt starts with stable mode identity and shared rules.
- Tool schemas are passed structurally, not pasted into prose.
- Dynamic `environment_details` are attached to user turns rather than mixed into the beginning of the system prompt.

Risky:

- The system prompt still includes mode lists and skills that can change.
- User custom instructions can include many rule files from multiple locations, making reproducibility difficult.
- The current mode changes the first line of the system prompt, which means switching modes changes the earliest prefix.
- If provider tool schemas are included before the system prompt for a given provider, large tool changes can affect cache prefixes.
- Environment details can be large and are added every turn.

The biggest practical win is not "more embeddings." It is controlling prompt volatility and measuring actual token/cost behavior.

## Why The Current Mode Set Feels Heavy

There are several overlapping concepts:

- Modes define role and tool access.
- Tools define capabilities.
- Custom modes define workflows.
- Skills define additional instructions and slash commands.
- Rules define project behavior.
- MCP defines external tools/resources.
- Code index defines retrieval.
- Task delegation defines multi-agent workflow.

Each layer is individually defensible. Together, they produce a product where users must understand too much internal taxonomy.

The user-facing mode list should be smaller than the internal capability graph.

## Where Alpha Has Drifted

The architecture appears to have drifted in these ways:

1. Modes became both UX concepts and permission bundles.
2. Orchestrator became a visible mode instead of an internal planning/delegation capability.
3. Prompt behavior is distributed across too many files and state stores.
4. Rules support both new `.alpha` paths and legacy `.roo`/`.cline` paths, which is useful for compatibility but confusing.
5. The system prompt is generated dynamically but there is no single human-readable "prompt trace" artifact.
6. Code index configuration is powerful, but the user-facing value proposition is not clear: users see "embeddings" but not exactly when they save tokens or improve answers.
7. Ask, Code, Debug, Architect, Orchestrator, and many project modes compete for mental space.

This is less a code bug than an experience design issue.

## Recommended Product Model

Keep these as the primary visible modes:

- Ask: answer, explain, compare, document, inspect. No file edits by default.
- Code: plan, inspect, edit, run commands, test, and optionally delegate internally.
- Debug: diagnose failures, collect evidence, add instrumentation when needed, then fix.

Make orchestration an internal capability:

- Code can spawn/delegate child tasks when the request is large.
- Debug can delegate focused investigation or reproduction tasks.
- Ask can propose a workflow but should not spawn editing subtasks unless user escalates.

Architect can either:

- remain as an advanced planning mode, or
- become a behavior inside Ask/Code triggered by "plan first" or by large task detection.

The best version for the user request is: "Orchestrator is always set to Code unless the user explicitly asks for pure coordination."

## Recommended Prompt Architecture

Introduce a prompt manifest or trace view that shows:

- Selected mode and source.
- Role definition source.
- Prompt override source.
- Tool groups and final allowed tools.
- Disabled tools and why.
- Rule files included, in exact order.
- Agent files included, in exact order.
- Skills included.
- MCP servers/resources included.
- Dynamic environment fields included.
- Approximate token count by section.
- Cache classification: stable, semi-stable, volatile.

This can be generated without changing model behavior. It would make the system inspectable.

Then reshape the actual prompt into clear layers:

1. Static product policy and mode role.
2. Stable tool-use policy.
3. Stable project rules.
4. Semi-stable mode and skill context.
5. Dynamic environment details.
6. User message.
7. Tool results and retrieved snippets.

The earlier a section appears, the more stable it should be.

## Recommended Storage Architecture

Create a single "effective task configuration" object per task. It should snapshot:

- Mode slug.
- Mode definition hash.
- Custom prompt override hash.
- Global custom instruction hash.
- Included rule file paths and hashes.
- Included `AGENTS.md` paths and hashes.
- Enabled tools.
- Provider/model.
- Code-index config summary.
- MCP server list summary.
- Prompt version.

Store this with the task metadata. This makes old task behavior explainable later even if global settings change.

Keep secrets and vector data where they are, but expose non-secret configuration and hashes in the task trace.

## Recommended Code Index Improvements

Improve retrieval quality and cost by focusing on precision:

- Use smaller default search result counts for chat injection.
- Add per-result token budgets.
- Prefer returning file path, symbol name, line range, and a compact excerpt first.
- Encourage the model to read exact files after retrieval before editing.
- Track which retrieved chunks were later useful.
- Tune score thresholds by embedding model profile.
- Deduplicate nearby chunks from the same file.
- Consider hybrid search: lexical search plus vector search.
- Add query rewriting only when the first search fails.
- Avoid embedding generated, build, vendor, and lock files by default.
- Show index freshness and last indexed commit or file hash summary.

## Performance And Cost Recommendations

Measure before changing defaults:

- Input tokens per request.
- Output tokens per request.
- Cached input tokens.
- Cache creation/read tokens where supported.
- Tool schema token contribution where visible.
- Environment-details token contribution.
- Retrieved code chunk token contribution.
- Number of codebase searches per task.
- Number of file reads after retrieval.
- Embedding tokens and embedding cost.
- Indexing time and files skipped due to cache.
- Vector search latency.

Then optimize:

- Move volatile context later.
- Reduce repeated `environment_details` content.
- Only include full workspace file list on the first turn or when explicitly useful.
- Make git status opt-in or compact by default.
- Cap terminal output aggressively.
- Cap retrieved chunks by token budget, not only count.
- Separate "explain" responses from "edit" responses so Ask does not inherit implementation overhead.
- Keep Code as the main capable mode and make delegation automatic but invisible unless it happens.
- Cache or memoize generated system prompt sections by source hash.

## Answering The Core Questions

### Where is the system prompt?

It is generated in `src/core/prompts/system.ts` by `SYSTEM_PROMPT`.

It is previewed through `src/core/webview/generateSystemPrompt.ts`.

It is used at runtime by `src/core/task/Task.ts` when calling `api.createMessage(...)`.

### What is the system prompt?

It is the current mode's role definition plus shared instructions, capabilities, mode list, skills, rules, system info, objective, and user/project custom instructions.

It is not one static string.

### How is everything generated?

The task reads extension state, selected mode, custom modes, custom prompt overrides, settings, MCP state, skills, rule files, `AGENTS.md`, ignore rules, workspace context, and model info. It assembles prompt sections, builds native tools, filters tools by mode, appends dynamic environment details to the conversation, and sends the result to the provider.

### Do we need all these modes?

Probably not as user-facing choices.

Ask, Code, and Debug make sense. Orchestrator makes more sense as an internal capability of Code than as a separate thing users must choose. Architect may be useful for advanced workflows, but for most users it can be an Ask/Code behavior.

### Does embedding code save tokens?

Only when retrieval replaces sending larger amounts of code. Embeddings do not reduce the token cost of retrieved chunks that are later injected into the chat prompt.

### What is the enhancement from embeddings?

The enhancement is selective retrieval: finding likely relevant code snippets in a large workspace without reading many files. The benefit is better context selection, not free context.

### How can Alpha improve performance and model cost?

The highest-impact changes are prompt tracing, reducing volatile injected context, keeping stable prompt prefixes stable, measuring cache hit rates, limiting retrieved chunk tokens, simplifying visible modes, and turning orchestration into a capability rather than a mode.
