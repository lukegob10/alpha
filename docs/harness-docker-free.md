# Docker-free evaluation

Docker is optional infrastructure coverage, not a prerequisite for evaluating the real extension. The primary local loop is the VS Code 1.122.1 host campaign documented in [testing-harness.md](testing-harness.md): deterministic providers, scenario receipts, evidence capture, actual extension/runner digests, and paired reports all run without PostgreSQL, Redis, or Docker. Live providers remain explicitly budgeted supplemental runs.

The evaluator package has three distinct dependency boundaries:

| Workflow                                                                       | Dependencies                                                            | State changes                                                                                 |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `pnpm test:evals:offline`, exact-host campaigns, host export and paired report | Node/pnpm; VS Code for host execution                                   | Local temporary workspaces and retained evidence                                              |
| `pnpm --dir packages/evals services:check`                                     | Configured PostgreSQL and Redis                                         | Read-only `SELECT 1` and `PING`; no migration/reset                                           |
| `pnpm --dir packages/evals test:services`                                      | Dedicated local `evals_test` database with migrations; configured Redis | Database tables truncated by integration setup; unique short-lived Redis lease/heartbeat keys |
| `pnpm --dir packages/evals test:docker`                                        | Docker and required images                                              | Container isolation/resource/outage contracts                                                 |

`test:all` retains all coverage. The compatibility `test:infrastructure` command retains Redis plus Docker contracts. `docker:prepare`, `docker:campaign`, and `docker:stop` explicitly select the optional container workflow.

For corporate service validation, provision approved native or externally managed services independently of this repository. Set `DATABASE_URL` and `REDIS_URL` in the calling environment; package commands load `.env.test` without overriding existing environment values. `REDIS_URL` is required, with no test fallback to a possibly unrelated default instance. For a locally provisioned test Redis on port 6380, its value is `redis://localhost:6380`. Readiness never prints either URL or connection error details and bounds probes to six seconds plus bounded PostgreSQL shutdown.

Readiness can inspect approved remote endpoints, but destructive integration tests reject remote targets. The test database URL must use `postgres:` or `postgresql:`, exact loopback hostname (`localhost`, `127.0.0.1`, or `[::1]`), database `/evals_test`, and no query/fragment overrides. This rejects credentials, hostnames, or query strings that merely contain `localhost`/`test`. Running `test:services` explicitly authorizes resetting that dedicated database; do not point it at valuable data. No remote destructive-test override is provided. Provision/migrate the isolated database under the organization's normal authorization before running the tests.

The existing full benchmark controller also supports a local process backend: PostgreSQL persists runs/tasks/trials/attempts/evidence, and Redis owns runner leases, heartbeats, and pub/sub. Those services are genuine dependencies of that controller, independent of Docker. Benchmark tasks use disposable workspaces, and the controller does not reset or commit the source checkout. Mixed benchmark/legacy checkout ownership is rejected. Legacy exercise runs retain their dedicated-checkout workflow; reset and commit now reject a subdirectory of a parent Git checkout before any mutation. They should never use a shared development checkout.

The local VS Code adapter launches the installed `code`/`code.cmd` with argument-safe paths and uses Windows named pipes or native temporary sockets. It requires the compatible installed extension and IPC configuration; it does not attest that installation as the current source build. Its campaign receipt therefore remains incomplete for strict harness pairing. Use the actual-host campaign path for build-attested comparisons. This change does not certify a native full-controller live run: no service or paid-provider run was performed during implementation.

Local process/worktree separation is **not a security sandbox**. Private grader files outside a task workspace are not confidential from arbitrary processes running as the same OS user, and local network restrictions are not enforced by a folder layout. Use trusted deterministic fixtures locally; confidential or adversarial grading requires an independently approved execution boundary. Docker-specific isolation claims remain confined to the optional container contracts.

Validation for this change: all 251 evaluator unit tests passed, including focused URL-guard, readiness, controller checkout-ownership, dedicated-checkout, and launch tests; evaluator TypeScript check passed. Service integration and native live-controller execution require separately provisioned approved services and were not claimed as passed.
